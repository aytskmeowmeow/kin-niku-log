# 開発フロー

## 目的

仕様はユーザーが決め、受け入れ要件をテストで固定し、実装を受け入れ要件から隔離することで、仕様どおりの実装と、ユーザーが理解したうえでのマージを両立させる。委譲は隔離が必要なときだけにして、速度とトークン効率を保つ。

## 参照

- ルール本体は `references/rules.md`。開発タスクに着手する前に必ず読むこと(関連スキルとの分担も rules.md に書いてある)。

## 実行手順

1. `references/rules.md` を読む
2. タスクの文書(kn-task-docs の配置)を確認し、フローのどの段階にいるかを判断する
3. rules.md の「フロー」の段階を順に進める。その前に、ルートを判断する(判断の基準と例は rules.md の「運用ルート」の対象の定義。迷ったらユーザーに聞く):
   - 既存タスクの中で出た修正(PR レビュー対応、理解度チェック後の改善提案)は、次の順に見る:
     1. 仕様の変更を伴う(基準は rules.md の「運用ルートの小さな修正」の節) → 元のタスクのフロー(アプリのコード・振る舞いにも触れるなら通常のフロー)
     2. アプリのコード・振る舞いに触れる小さな修正(単体テストだけの修正を含む) → 「軽量ルート」
     3. アプリのコード・振る舞いに触れない小さな修正(受け入れテストだけの修正を含む) → 「運用ルートの小さな修正」
   - 新しく始めるタスクは:
     - スキル・hook・設定・ドキュメントだけを変え、アプリのコード・振る舞いに触れない → 「運用ルート」
     - それ以外 → 通常のフロー
4. 仕様の疑問は rules.md の「エスカレーション」に従い、決定を design.md に転記してから再開する
5. PR を作る前に、理解度チェックを終えていることを確認する
