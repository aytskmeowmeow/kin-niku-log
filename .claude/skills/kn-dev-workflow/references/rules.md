# 開発フロー — ルール本体

関連スキルとの分担: 文書の書式・編集者・ドキュメントレビューの契機は **kn-task-docs**、コードレビューの観点は **kn-code-review**、コミットの規約は **kn-commit-workflow**。このファイルはフローの手順を持つ。

## 原則

### 1. 作業は原則メインが直接やる

調査・文書作成・テスト作成・コミット・検証は、メイン(ユーザーと会話しているエージェント)が直接行う。委譲のたびにプロンプト作成と成果物の受け取りの往復が乗り、速度もトークン効率も落ちる。調査も、結果を受け取って使う段階でトークンが増えることがあるので、メインが直接行い、その結果で文書を書く。

### 2. サブエージェントに渡すのは、コンテキストの隔離が必要な作業だけ

| 作業 | 担当 | 隔離する理由 |
|---|---|---|
| 実装 | `kn-implementer` | 受け入れ要件(acceptance.md と受け入れテスト)を見せずに実装させる。テストを通すこと自体が目的になり、実装が仕様からずれるのを防ぐ。kn-implementer は Docker Sandboxes の VM の中で動かし、受け入れ要件を除いた作業場所だけを渡す(手順は 4)。**運用ルートとその小さな修正では、メインが直接実装する。** 運用ルートには隠す受け入れ要件が無い。運用ルートの小さな修正はアプリのコード・振る舞いに触れず、隔離が要らない(受け入れテストの修正は、そもそも kn-implementer が読めない) |
| ドキュメントレビュー | `kn-doc-reviewer` | 文書を書いたのはメイン。書いた本人は自分の穴に気づきにくい(reviewer != author) |
| コードレビュー | `kn-code-reviewer` | メインは acceptance.md と impl.md の author なので、セルフレビューをしない。運用ルートとその小さな修正では、メインがコードの author でもある |

サブエージェントに渡すタスクは小さく切る。1 体で足りるなら 1 体にする。上の 3 つ以外の理由では委譲しない。

### 3. 仕様はユーザーが決める

メインもサブエージェントも、「たぶんこうだろう」で仕様を決めない。フェーズの配置やスコープも仕様の判断に含む。疑問は「エスカレーション」に従う。

## フロー

```
0. 開始 → 1. 受け入れ要件 → 2. 受け入れテスト → 3. 方針 → 4. 実装 → 5. 検証 → 6. レビュー
→ 7. コミット → 8. 動作確認 → 9. 理解度チェック → 10. PR
```

4〜6 は、指摘や未達があれば 4 に戻る。

### 0. 開始

- kn-task-docs の「配置」に従って文書のディレクトリを作る
- design.md をユーザーと作る。**外から見た契約(API は `openapi.yaml`、画面の操作)をここで決める**
- 既存タスクの再開なら、design.md / acceptance.md(あれば)/ impl.md を読んでから入る

### 1. 受け入れ要件

- メインがユーザーとの会話から acceptance.md を起案する(書式は kn-task-docs)
- 各要件に確認方法 ①自動テスト ②Claude が localhost で確認 ③ユーザーの手動確認 を付ける
- kn-doc-reviewer にレビューさせる(毎回新しく起動する。観点: design.md の要件を漏れなく網羅しているか)
- ユーザーに「承認済み」にしてもらう。**承認されるまで 2 に進まない**

### 2. 受け入れテスト

- メインが ① の要件をテストにする。対象は外から観測できる振る舞いだけ(API の入出力、画面の操作)。内部構造に依存させない
- 置き場所はパスに `acceptance` を含める(VM の作業場所からの除外と、acceptance ガードの判定に使う)
- 全件が red になることを確認し、**実装の前にコミットする**(テストを変えずに通したことを、後から差分で確かめられるようにする)。このコミットに design.md と acceptance.md も含める

### 3. 方針

- メインが impl.md を書く(構成・技術的判断・実装状況)
- kn-doc-reviewer にレビューさせる(毎回新しく起動する。観点: design.md ↔ impl.md)。レビューの指摘を反映したら impl.md をコミットする

### 4. 実装

`kn-implementer` に渡す。kn-implementer は Docker Sandboxes の VM の中で、`.claude/scripts/kn-sandbox.sh` を使って動かす。**Agent ツールでは起動しない**(受け入れ要件のある作業ツリーで動いてしまう)。`<タスク>` は文書のディレクトリ名(例: `23-meal-log`):

1. タスクの最初の委譲の前に `kn-sandbox.sh create <タスク>`(VM を作り、bun を入れ、GitHub への通信を止める)。`sbx` が無いときは、ユーザーに導入と VM の中での `/login` を依頼する
2. 委譲のたびに `kn-sandbox.sh prepare <タスク>`(今の作業ツリーから受け入れ要件を除いて書き出し、規約スキルを写す)
3. 委譲プロンプトを `~/.cache/kn-sandbox/<タスク>/prompt.md` に書き(リポジトリの中に書くと、次の prepare で作業場所に書き出される)、`kn-sandbox.sh run <タスク> <そのファイル>` を Bash のバックグラウンドで動かす。標準出力が kn-implementer の報告
4. `kn-sandbox.sh collect <タスク>` で変更を作業ツリーに取り込む
   - run の間、メインは kn-implementer の範囲のファイルを変えない。同じ箇所を変えると collect が衝突で止まる(何も取り込まない)。prepare は、取り込んでいない変更があれば止まる(`--force` で捨てる)
   - 次のどれかに触れる変更が 1 つでもあれば、collect は何も取り込まない: 受け入れ要件のパス、どの階層の `.claude/`・`CLAUDE.md`・`CLAUDE.local.md`、ルートの `.mcp.json`、`docs/` の下の design.md・acceptance.md・impl.md、シンボリックリンク。拒まれたら、prepare せずに `run --continue` で kn-implementer にその変更を戻させてから collect し直す
5. PR がマージされたら `kn-sandbox.sh rm <タスク>`。VM が壊れたら `kn-sandbox.sh recreate <タスク>`(VM だけを作り直す。VM の中の会話は消えるので、次の run は `--continue` を付けずに引き継ぐ)

委譲プロンプトに含めるもの:

- design.md / impl.md のパス(リポジトリのルートからの相対パス)と「まず読め」
- 今回の範囲(impl.md の実装状況の項目)と、範囲外の変更をしないこと
- 戻りの場合は、直すべき点(下の「実装エージェントへの戻し方」の形)

実装エージェントの振る舞いはエージェント定義に書いてある(単体テストは自由に書く / impl.md は書かない / git に書き込まない / 疑問は仕様の言葉で返す)。

**1 issue の中では同じ kn-implementer の会話を使い続ける**(`run` に `--continue` を付けて続きを渡す)。コンテキストが膨らんだら、成果と未完了を報告させ、`--continue` を付けずに新しい会話で引き継ぐ。

実装エージェントの報告を受けたら、collect してから、メインが impl.md の実装状況を更新する。

**実装エージェントがテスト・仕様の誤りを指摘してきたら:** テストの誤りならメインが直す。仕様の誤りなら design.md の未決事項に上げる。

### 5. 検証

メインが実行する:

1. `bun run lint` / `bun run check-types`
2. 単体テスト・受け入れテスト(①)
3. ② の要件を localhost + ブラウザで確認する

**テスト基盤が入るまで**(Phase 3 の最初の issue で入れる)は、1 に加えて `bun run build` を検証とし、テストを省いたことを impl.md に記録する。黙って省かない。

未達は 4 に戻す。

### 6. レビュー

`kn-code-reviewer` に渡す(毎回新しく起動する)。渡すもの:

- design.md / acceptance.md(あれば。運用ルートのタスクでは無いことを伝える)/ impl.md のパス
- 対応を見送った指摘・未決事項に上げた指摘の一覧(2 回目以降。同じ指摘を出し直させないため)
- 今回の差分(ベースのコミットと変更ファイルの一覧)

返ってきた指摘を分類する:

| 分類 | 扱い |
|---|---|
| 仕様・設計に関わる(design.md に書かれた・書かれるべき情報に触れる) | design.md の未決事項に上げ、ユーザーの判断を待つ(受け入れ要件を引用せず、design.md の言葉で書く) |
| 実装で閉じる | 4 に戻す |
| 対応しない | 理由を impl.md に残す |

迷ったら仕様・設計側に倒す。指摘と対応は impl.md の「レビュー指摘と対応」に記録する。design.md と impl.md は kn-implementer に渡るので、どちらに書くときも「実装エージェントへの戻し方」と同じく、受け入れ要件を引用せず design.md の言葉で書く。レビュアーが挙げた「lint 化の候補」も同じ節に、レビュー回ごとに `- lint 化の候補: <内容、または「なし」>` の 1 行で記録する(指摘の件数には数えない。10 の集計がこの書式で拾う)。

**未対応の指摘(見送り・未決事項に上げたものを除く)が 0 件になり、検証が通るまで 7 に進まない。**

### 実装エージェントへの戻し方

検証(5)の未達もレビュー(6)の指摘も、**メインが design.md の言葉に言い換えてから**実装エージェントに渡す。

- 渡さないもの: テストの失敗メッセージ(期待値・実際の値)、テストコード、acceptance.md の文面、レビュー指摘のうち受け入れ要件を引用した部分
- 渡すもの: 「design.md の <節> の <要件> が満たされていない。<観測された振る舞い> になっている」

### 7. コミット

- メインが kn-commit-workflow に従ってコミットする。**ユーザーの承認は取らない**
- force push・push の確認・コミット規約の強制は hook が担う。hook に止められたら、回避せず原因を直す

### 8. 動作確認

③ の要件の確認をユーザーに依頼する。依頼には、確認する AC の番号と手順を書く。

### 9. 理解度チェック

issue の作業がすべて終わった後、PR を作る前に、issue(issue にしないタスクではタスク)ごとに 1 回行う。目的は、ユーザーが理解していないコードをマージしないこと。

1. メインが差分と design.md から 3〜5 問出す。観点:
   - なぜこの設計にしたか(design.md の決定との対応)
   - 異常系でどう動くか
   - 変更がどこに影響するか
   - どこを見ればその挙動が分かるか
2. ユーザーが自分の言葉で答える。メインが評価し、ずれていたら解説する
3. **ユーザーが説明できるようになるまで、解説と再質問を続ける。それまで PR を作らない**
4. 説明できるようになったら、ユーザーが「このまま進む」か「コードの改善を提案する」かを決める
   - 理解できなかった原因が、ユーザーの理解不足かコードの分かりにくさかは、この時点では分からない。改善はユーザーの提案を起点にする
   - **メインはチェックの結果から独断でコードを書き換えない**
   - 改善の提案は軽量ルートで対応する(アプリのコード・振る舞いに触れないものは「運用ルートの小さな修正」、仕様の変更を伴うものは元のタスクのフローで対応する)
5. 結果を impl.md の「理解度チェック」節に残し、push の前にコミットする(書式は kn-task-docs)

### 10. PR

- lint 化の候補を集める。`git grep -n "^- lint 化の候補:" -- "docs/**/impl.md"` で各タスクの impl.md に残った候補を集め(「なし」の行は除く)、件数と中身をユーザーに報告する。今回のタスクのディレクトリのヒットを「今回増えた分」として分けて示す。lint 化のタスクを起こすかはユーザーが決める
- ブランチを push する(push 確認 hook でユーザーが承認する)
- PR を作る。本文に design.md / acceptance.md(あれば)/ impl.md へのリンクを入れる
- gh の書き込みが hook に止められたら、回避せずユーザーに実行を依頼する

## 軽量ルート

**対象:** 仕様の変更を伴わず、アプリのコード・振る舞いに触れる小さな修正(判断の基準と例は「運用ルート」の対象の定義)。PR レビュー対応、理解度チェック後の改善提案など。アプリのコード・振る舞いに触れない小さな修正は、タスクの種類を問わず「運用ルートの小さな修正」で扱う。

```
メインが軽量ルートに乗せると判断し、impl.md に 1 行残す
→ 4. 実装(kn-implementer。隔離を保つため、メインは書かない)
→ 5. 検証
→ 6. レビュー(kn-code-reviewer)
→ 7. コミット
→ push(PR レビュー対応のように既存の PR がある場合。push 確認 hook でユーザーが承認する)
```

- 省くのは、ドキュメントレビューと理解度チェック
- ③ の動作確認は、修正が ③ の要件に関わる場合だけ依頼する
- 仕様に触れると分かった時点で、通常のフローに戻す

## 運用ルート

**対象:** 新しく始めるタスクのうち、スキル・hook・設定・ドキュメントの変更で、アプリのコード・振る舞いに触れないもの(既存タスクの中で出た小さな修正は、軽量ルートか「運用ルートの小さな修正」で扱う)。判断の基準は「アプリのコード・振る舞いに触れるか」で、ファイルの場所ではなく変更の内容で決める。下に並べたものは例で、ここに無いものも同じ基準で判断する(軽量ルートと「運用ルートの小さな修正」も、この基準と例で振り分ける)。

- 運用ルートで扱うもの: スキル・hook・ドキュメントの変更。設定のうち、アプリの振る舞いが変わらないことを lint / check-types / build / テストで確かめられる変更(lint・型の設定、package.json の scripts など。共有の `packages/eslint-config/`・`packages/typescript-config/` を含み、`apps/*` の下の設定ファイルも内容で判断する)
- 通常のフロー(小さな修正なら軽量ルート)で扱うもの: アプリのソース(`apps/`・`packages/` のソース)の変更(リファクタリングを含む)、依存ライブラリの更新(メジャーに限らず、バージョンの上げ下げすべて)、ビルド・デプロイ・コード生成の設定(vite・cloudflare・drizzle・orval など)の変更、DB のマイグレーション・静的ファイル(`index.html`・`public/`)の変更
- テストコード: 単体テストはアプリのソースとして扱う(小さな修正なら軽量ルート)。受け入れテストだけの修正は、`apps/` の下にあってもアプリのコードとして扱わない(運用ルートの小さな修正)
- 迷う例: tsconfig のうち、ビルドの出力にも効く設定(`jsx`・`useDefineForClassFields`・`verbatimModuleSyntax`・`experimentalDecorators` など。vite などが使う esbuild が読む)
- 振る舞いに影響するか迷ったら、ルートを選ぶ前に理由を添えてユーザーに聞く

```
0. 開始(design.md。issue にしないタスクは docs/<slug>/)
→ 3. 方針(impl.md。kn-doc-reviewer のレビューあり。レビューを反映したら design.md と impl.md をコミットする)
→ メインが直接実装する
→ 検証(hook ならテストケースを流す、など対象に合わせて。方法を impl.md に残す)
→ 6. レビュー(kn-code-reviewer)
→ 7. コミット → 9. 理解度チェック → 10. PR
```

- 省くのは、受け入れ要件(1)・受け入れテスト(2)・動作確認(8)。隠す受け入れ要件が無いので、実装は委譲しない
- ユーザーの環境でしか確かめられない確認(グローバル設定の変更など)が要るときは、impl.md の検証方法に「ユーザーに確認を依頼」と書き、コミット後に依頼する
- 完了条件は design.md の要件・決定事項。kn-code-reviewer にも acceptance.md が無いことを伝え、design.md と照合させる
- 検証: リポジトリの設定・ツール設定(tsconfig・lint の設定・package.json の scripts など)かテストコードに触れる場合は、5 の 1(`bun run lint` / `bun run check-types`)と `bun run build` も実行する。テスト基盤が入った後(Phase 3 から)は、触れた範囲によらず、単体テストと受け入れテストを毎回実行する
- メインが author になるので、コードレビューは必ず kn-code-reviewer に渡す(セルフレビューで代えない)
- 検証の未達・レビューの指摘で戻るときは、メインが直接直す。「実装エージェントへの戻し方」の言い換えは要らない。進行報告の「lint / テスト / ② の結果」は、impl.md に残した検証方法の結果に置き換える(レビュー指摘の件数はそのまま報告する)
- 理解度チェックは省かない(issue にしないタスクでは、タスクごとに 1 回)
- アプリのコード・振る舞いに触れる(対象の定義で「通常のフロー」に当たる)と分かった時点で、通常のフロー(小さな修正なら軽量ルート)に戻す

### 運用ルートの小さな修正

仕様の変更を伴わず、アプリのコード・振る舞いに触れない小さな修正(判断の基準と例は「運用ルート」の対象の定義)。通常のフローのタスクか運用ルートのタスクかは問わない。理解度チェック後の改善提案や PR レビュー対応(design.md の記述の修正、lint の設定の修正など)。

- design.md の修正のうち、要件・仕様・決定事項の中身を変えるものは仕様の変更として扱う。古くなった記述の更新、決定事項の転記漏れ、表記の修正は小さな修正として扱う
- 受け入れテストだけの修正(acceptance.md を変えないもの)もここで扱う。kn-implementer は受け入れテストを読めず、受け入れテストはもともとメインが書くため。acceptance.md を変えるなら仕様の変更として扱う

```
メインが直す → 検証(運用ルートと同じ)
→ 6. レビュー(kn-code-reviewer)
→ 7. コミット
→ push(既存の PR がある場合。push 確認 hook でユーザーが承認する)
```

- 省くのは、ドキュメントレビューと理解度チェック
- 検証・コミット・push と周回の上限は、運用ルート・軽量ルートと同じ扱い(D9・D28)
- kn-code-reviewer には、通常のフローのタスクなら acceptance.md も渡す(design.md の修正と AC の食い違いを照合させるため)
- アプリのコード・振る舞いに触れると分かった時点で軽量ルートに移す
- 仕様に触れると分かった時点で、元のタスクのフロー(通常のフローか運用ルート)に移す。アプリのコード・振る舞いにも触れるなら、通常のフローに移す

## 周回の上限

- 実装の不備で 4 に戻った回数を数え、**上限 3 回**。検証(5)の未達で戻った場合と、レビュー(6)の指摘で戻った場合の両方を数える。軽量ルート・運用ルート(その小さな修正を含む)にも同じ上限を適用する(運用ルートでは、メインの実装が戻った回数を数える)
- 数えないもの: 文書の表記・時制などの修正(メインがその場で直す)、テストや仕様の誤りによる戻り(実装の不備ではない)
- ユーザーが仕様を新しく決めたら(決定事項の転記漏れの補完は含まない)、その反映は新しい実装として 0 から数え直す
- 上限に達したら、それ以上自分の判断で続けない。design.md の未決事項に次を書いてユーザーに返す:
  - 状況: 何回戻ったか、残っている未達・指摘、原因の見立て
  - 選択肢: ①さらに続ける ②スコープを縮めて受け入れる ③設計を見直す ④別タスクに切り出す
  - 推奨

上限は「実装が困難なとき」に止まるためのもの。

## エスカレーション

仕様・要件の疑問(design.md から答えが出ない選択)は、発生源を問わず(サブエージェント・メイン自身・タスク着手時)このルートに乗せる。サブエージェントは自分で判断せず、疑問と選択肢を返す。

| 判断の重さ | ルート |
|---|---|
| 軽い(選択肢が 2〜4 個、トレードオフが 1 行で書ける) | AskUserQuestion。1 往復で閉じなければ design.md ルートに切り替える |
| 重い(論点が複数 / 後から根拠を追いたい / 後続のタスクに影響する) | design.md の未決事項に「疑問 / 選択肢 / トレードオフ / 推奨」を書き、チャットでは「design.md の <節> に判断を書いてください」と伝えて止まる |

**どちらのルートでも、ユーザーの決定を design.md の決定事項に転記してから作業を再開する**(手順は kn-task-docs)。ユーザーがチャットで答えた場合も同じ。口頭の合意のまま進めない。

仕様に影響しない技術的な判断(内部設計・ライブラリの使い方)はエスカレーション不要。impl.md の技術的判断に理由を残す。迷ったらエスカレーションに倒す。

## 進行報告

- 段階が進むたびに、何が終わって次に何をするかを短く報告する
- 4〜6 の周回では「第 N 回: lint / テスト / ② の結果、レビュー指摘 X 件(うち仕様 Y 件)」だけを報告し、指摘の中身は impl.md を見てもらう
- ユーザーに判断を求めるのはエスカレーションと、受け入れ要件の承認・動作確認・理解度チェックだけ
