# タスク文書 — ルール本体

## なぜこの運用か

- **セッションをまたげる** — 会話が失われても、文書を読めば作業を再開できる
- **委譲が軽くなる** — サブエージェントにはパスを渡すだけで済む
- **決定が遡れる** — 仕様の決定と理由が 1 か所に集まる
- **隠すべきものを分けられる** — 受け入れ要件(acceptance.md)を実装エージェントから隔離できる

「会話の中だけで決まったこと」はセッションが終われば消える。決定はファイルに置く。

## 配置

| タスクの種類 | 置き場所 |
|---|---|
| GitHub issue のあるタスク | `docs/issues/<番号>-<slug>/` |
| issue にしないタスク(エージェント運用など) | `docs/<slug>/` |

```
docs/issues/<番号>-<slug>/
├── design.md       # 仕様・要件
├── acceptance.md   # 受け入れ要件(実装エージェントには非公開)
└── impl.md         # 実装方針と現在地
```

**作る順番:** design.md → acceptance.md → impl.md。どれも実装に入る前に作る。acceptance.md は、調査だけのタスク、またはスキル・hook・設定・ドキュメントだけを変えるタスク(kn-dev-workflow の「運用ルート」)では作らない。

## 3 文書の役割

| 文書 | 中身 | 編集者 | 読める人 | 承認 |
|---|---|---|---|---|
| design.md | 仕様・要件・決定事項・未決事項 | ユーザーとメイン | 全員 | 仕様の決定者は常にユーザー |
| acceptance.md | 受け入れ要件(判定条件) | メイン(ユーザーとの会話から起案) | メイン・ユーザー・レビュー用エージェント。**実装エージェントは読めない** | ユーザーが「承認済み」にする |
| impl.md | 実装方針・現在地・レビュー記録・理解度チェック | **メインだけ**(実装エージェントは報告し、メインが反映する) | 全員 | ユーザーがレビューする |

## design.md

含める内容:

- **目的・背景** — なぜ作るか
- **要件** — 機能要件・非機能要件
- **仕様** — 外から観測できる振る舞い。**外から見た契約(API のパスと入出力は `openapi.yaml`、画面の操作)は、実装の前にここで決める**。受け入れテストは契約だけに依存して書くため、契約が決まっていないとテストが書けない
- **決定事項** — `D<番号>` の表(決定日 / 内容 / 理由)
- **未決事項** — `U<番号>`。疑問 / 選択肢 / トレードオフ / 推奨

実装エージェントが仕様を知る手段は design.md だけ。acceptance.md を隠しても仕様が伝わるよう、要件・仕様は design.md に書き切る(acceptance.md と重複してよい)。

**ユーザーの決定なしに仕様を書き換えない。未決事項を勝手に決定済みにしない。**

### 未決事項 → 決定事項の移動

ユーザーが判断した項目(design.md に直接書き込まれた場合、チャットで答えた場合を含む)は、メインが次を行ってから作業を再開する:

1. 未決事項から消す
2. 決定事項に転記する。決定日・内容・理由(どの選択肢をなぜ選んだか)を書く。ユーザーの補足は理由に残す
3. 覆された決定は、新しい決定で置き換え、旧内容は「変更履歴」に残す

ユーザーの答えが新しい論点を含んでいたら、決めずに新しい未決事項にする。

## acceptance.md

冒頭に状態を置く:

```
- 状態: 承認待ち
- 状態: 承認済み(YYYY-MM-DD)
```

**ユーザーが「承認済み」にするまで、受け入れテストの作成に進まない。**

各要件の書式:

```
### AC-<番号>. <要件の短い名前>

- 種別: 機能 / 非機能
- 出典: design.md の該当要件
- 確認方法: ① 自動テスト / ② Claude が localhost で確認 / ③ ユーザーの手動確認
- Given <前提>
- When <操作>
- Then <期待する結果>
```

確認方法の分け方:

| 区分 | 対象 | いつ確認するか |
|---|---|---|
| ① 自動テスト | API の入出力、ロジック、ローカルで再現できる振る舞い | 実装前にテストを書き、検証で毎回実行する |
| ② Claude が localhost で確認 | UI の見た目・操作など、ローカルで立てれば見られるもの | 検証(コミット前)で確認する |
| ③ ユーザーの手動確認 | デプロイ・本番・外部サービスなど、ローカルで再現できないもの | コミット後、動作確認として依頼する |

**網羅:** design.md の機能要件・非機能要件のそれぞれに、少なくとも 1 つの AC が対応していること。ドキュメントレビューで確かめる。

**受け入れテストの置き場所:** パスに `acceptance` を含める(ディレクトリ名かファイル名)。実装エージェントの acceptance ガード hook がこの規約で判定する。

## impl.md

含める内容:

- **実装状況** — 項目ごとの 完了 / 進行中 / 未着手 と、確認した事実
- **構成** — 変更・追加するファイルと役割
- **技術的判断** — design.md の仕様をどう実現するか、選択の理由
- **検証方法** — 運用ルートのタスクで、何で確かめたか(ユーザーに確認を依頼するものはそう書く)
- **既知の制約・未解決の疑問**
- **レビュー指摘と対応** — 下の書式
- **理解度チェック** — 下の書式

「コードを読めば分かること」は書かない。読み取りにくい判断・経緯・全体像を書く。古くなった記述は追記ではなく**置き換え**る。

### レビュー指摘と対応の書式

```
### レビュー第 N 回(YYYY-MM-DD、<ドキュメント / コード>)

- **指摘:** <箇所と問題の要約>
  - **対応:** <採用した対応と理由>
  - **状態:** 対応済み / 対応見送り(理由)
```

件数が多い回は、区分ごとの表にまとめてよい。コードレビューの回は、末尾に `- lint 化の候補: <スキル名 / ルール / 根拠、または「なし」>` を 1 候補 1 行で置く(kn-dev-workflow の 10 がこの書式で集める)。

### 理解度チェックの書式

```
## 理解度チェック(YYYY-MM-DD)

| # | 質問 | 観点 | 回答の要点 | 解説した点 |
|---|---|---|---|---|

- ユーザーの判断: このまま進む / 改善を提案(提案内容)
```

観点は「なぜこの設計か / 異常系 / 影響範囲 / どこを見れば挙動が分かるか」のいずれか。

## ドキュメントレビューの契機

メインが書いた文書は、**メイン以外の kn-doc-reviewer** にレビューさせる(reviewer != author)。kn-doc-reviewer は毎回新しく起動し、前回のレビューを続けさせない。

| 契機 | レビュー | 観点 |
|---|---|---|
| acceptance.md の初版作成 | 必須 | design.md の要件を漏れなく網羅しているか。判定条件が観測可能か |
| acceptance.md の要件の追加・変更 | 必須 | 同上 |
| impl.md の初版作成 | 必須 | design.md ↔ impl.md の整合 |
| impl.md の「構成」「技術的判断」への書き込み | 必須 | 同上 |
| design.md の変更直後の impl.md / acceptance.md の更新 | 必須 | 旧仕様の残留・反映漏れ |
| impl.md の「実装状況」だけの更新 | 不要 | — |
| 「レビュー指摘と対応」「理解度チェック」への追記だけ | 不要 | — |
| 表記・時制などの修正(方針を動かさない) | 不要 | — |

レビュアーの指摘の扱い:

- 記述の修正で閉じるもの(漏れ・過剰・表記) → メインがすぐ直し、「レビュー指摘と対応」に記録する
- 仕様に関わるもの(design.md と食い違う、未決事項を先取りしている、design.md に無い仕様を足している) → design.md の未決事項に上げてユーザーの判断を待つ

## design.md ↔ impl.md レビューの観点

- design.md の決定事項が impl.md に反映されているか
- impl.md の方針・技術的判断が design.md と矛盾していないか
- 未決事項の内容を、impl.md が決定済みのように扱っていないか
- design.md に無い仕様を impl.md が足していないか
- 記述が具体的すぎる(コードの書き写し)/ 抽象的すぎて現在地が読めない箇所

## ユーザーが design.md を編集したとき

「design.md に書いた」と言われたとき、またはユーザーが design.md を直接編集したと分かったとき:

1. design.md を読む
2. 前回把握していた内容との**差分**を特定する(未決事項への回答なら、決定事項への転記の手順に進む)
3. 差分が acceptance.md・impl.md・実装・進行中の作業に与える影響を洗い出す
4. 影響と対応方針をユーザーに報告してから反映する。acceptance.md / impl.md を更新したら、「ドキュメントレビューの契機」に従ってレビューさせる

差分の解釈に迷ったら、推測で進めずユーザーに確認する。

## セッション再開時

既存タスクに触れるときは、まず design.md と impl.md(メインなら acceptance.md も。あれば)を読んでから作業に入る。会話履歴や記憶だけで進めない。文書と実装が食い違っていたら、どちらが正か勝手に決めずユーザーに確認する。
