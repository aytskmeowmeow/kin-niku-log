# コードレビュー観点 — ルール本体

## 位置づけ

- kn-dev-workflow の「6. レビュー」「軽量ルート」「運用ルート」「運用ルートの小さな修正」で、`kn-code-reviewer`(サブエージェント 1 体)がこのチェックリストを使う
- レビュアーはコードの author ではない(実装は kn-implementer、運用ルートとその小さな修正ではメイン)。メインも acceptance.md と impl.md の author なので、レビューは別エージェントが行う
- レビュアーは acceptance.md を読んでよい。受け入れ要件の抜けに気づくため。指摘は、メインが言い換えてから実装エージェントに渡す
- 対象は working diff(コミット範囲を含む)。GitHub PR のレビューは公式 code-review プラグインを使う

## 読むもの

1. design.md(仕様・決定事項)
2. acceptance.md(あれば。受け入れ要件)
3. impl.md(構成・技術的判断・実装状況)
4. 差分(`git diff <ベース>`)と、変更されたファイルの周辺

## 6 つの観点

すべての観点を順に見る。どれかを飛ばさない。

### 1. 外部仕様遵守(design.md / acceptance.md)

外から観測できる振る舞いが仕様どおりか。

- design.md の要件・acceptance.md の AC のうち、実装されていない / 過剰に実装されたもの
- API の入出力・エラー時のレスポンスが design.md(`openapi.yaml`)と違う
- UI の状態遷移・表示条件が design.md と違う
- design.md に書かれていない領域の判断が必要なもの → 指摘ではなく「仕様への疑問」に出す
- acceptance.md の無いタスク(運用ルートのタスク)では、design.md の要件・決定事項を完了条件として照合する

### 2. impl.md との整合

- impl.md の構成・モジュール分割と実物のずれ
- impl.md の技術的判断と実装の食い違い
- impl.md の実装状況と実物の食い違い

### 3. バグ・エッジケース(差分内)

- null / undefined / 空配列 / 0 / 境界値・オフバイワン
- 例外・エラー時の分岐漏れ
- 並行性・順序依存(差分から判断できる範囲)
- ガード節・早期 return の抜け

### 4. デグレ影響(差分の外)

- 変更したシグネチャ・エクスポート・ファイル配置の呼び出し元への影響
- 削除・改名したものが他所から参照されていないか
- 過去のコミット・PR で意図された制約に反していないか(必要なら `git log` / `git blame` を見る。引用するときは SHA を付ける)

### 5. 保守性・可読性(差分内)

- 意味を捉えづらい命名
- 差分内で 3 回以上の類似コード
- 過剰なネスト、早期 return で潰せる分岐
- 低レベルの操作と高レベルの意図が同じ関数に同居している

### 6. コーディング規約(差分内)

コーディング規約スキル(ts-type-safety / neverthrow-coding-rules / function-signature-typing など、差分の言語・領域に当たるもの)のうち、lint で検出されないルールへの違反。

- 該当するスキルの規約を、Skill ツールで読み込んでから差分を見る(規約スキルはリポジトリの外、`~/.claude/skills/` にある)。SKILL.md がルール本体として `references/rules.md` を案内していたら、それも Read で絶対パスを指定して読む
- lint の設定(`packages/eslint-config/` と、各パッケージの `eslint.config.*`。`apps/*`・`packages/ui` など)で検出されるルールを確かめ、それは除く
- 指摘には違反したスキル名とルールを書く
- lint で検出されるものは「指摘しないもの」に当たる。lint 化できそうなルールに気づいたら、指摘とは別に、出力形式の「lint 化の候補」に挙げる

## 指摘しないもの

- linter / formatter / typechecker が検出するもの(型エラー、import 忘れ、整形、未使用変数)
- 差分の外にある既存の問題
- 実務で指摘しない好みの nitpick
- 意図的に抑止されているもの(`eslint-disable` / 理由付きの TODO など)

**強さで絞らない。** 上の除外に当たらないものは、確度が低くても挙げる。確度は各指摘に書き、取捨はメインが行う。

## 出力形式

```
## 仕様への疑問
- <design.md から答えが出ない点。選択肢があれば添える>(無ければ「なし」)

## 指摘
| # | 観点 | ファイル:行 | 内容と失敗するシナリオ | 修正案 | 分類 | 確度 |
|---|---|---|---|---|---|---|

分類: 仕様・設計 / 実装判断
確度: 高 / 中 / 低

## lint 化の候補
- <観点 6 で見つけた規約のうち、lint ルールにできそうなもの。スキル名・ルール・根拠>(無ければ「なし」)
```

指摘が無ければ「指摘なし」と明示する。「概ね良好」のような曖昧な返しはしない。

## 禁止事項

- コード・文書を編集しない。git・gh に書き込まない
- 裸の `cd` を使わない(絶対パスか `git -C <path>`)
- dotenv 系ファイル(`.env` / `.env.*` / `.envrc` / `.dev.vars*`)を開かない
- `python -c` / `node -e` / `bash -c` などのインライン実行をしない
