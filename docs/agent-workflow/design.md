- Phase 2 の最初のタスク。#23(API トークン最小化)→ #24(CD)→ Phase 3(アプリ実装)に進む前に、AI エージェントの作業フローを固める

## 受け入れ要件 doc の導入(ユーザー提案、2026-10-18)

### ユーザー案

1. design.md / impl.md に加えて、**受け入れ要件 doc** を作る
2. 実装の前に、受け入れ要件 doc に基づいて **テストを作る工程** を入れる
3. **実装エージェントには受け入れ要件 doc を読ませずに** 実装させる
4. テストが通れば(= 受け入れ要件を満たしていれば)OK とする

### 想定フロー(たたき台)

```
design.md(仕様・要件)
   ↓
メインがユーザーと acceptance.md(受け入れ要件)を作成 → ユーザー承認
   ↓
メインが acceptance.md からテストを書く → 全件 fail(red)を確認
   ↓
実装エージェント(acceptance.md・テストは読まない)が design.md / impl.md を元に実装
   ↓
機械的検証: lint + 受け入れテスト(green になるまで)
   ↓
レビュー → メインがコミット(D9)
```

### 前提として確認できた事実

- このリポジトリには現時点でテストの仕組みが無い(各 `package.json` に test スクリプトが無い)。受け入れテストを回すには、先にテスト基盤を入れる必要がある
- 既存の `kn-implement-review-loop` は「lint + テスト」を機械的検証ゲートにしているが、テスト未整備の場合は記録して skip する設計。受け入れテストを停止条件の中心に置くなら、skip は許されなくなる

## 現状スキルの問題点(洗い出し)

### (a) スキル本文から見つかったもの

**明確な不整合・バグ**

- A1. `kn-code-review-agent` の採点閾値が食い違っている。`SKILL.md` の手順 4 と `rules.md` の全体フローは「80」、`rules.md` の閾値節は「75」
- A2. `commit-workflow-flag.sh` はスキル名が `commit-workflow` / `*:commit-workflow` のときだけフラグを立てる。`kn-commit-workflow` を起動してもフラグが立たず、コミットがゲートで止まる(改修版を運用する上での障害)
- A3. ~~`kn-subagent-orchestration` は「git 書き込みはコミットエージェントに委譲」と定めるが、コミットゲートのフラグはセッション ID 単位。サブエージェントのスキル起動でフラグが立つかは未確認~~ → D9(メインがコミット)で解消

**抜けやすい構造**

- A4. 強制力があるのはコミットゲートだけで、他は全部「読んで守る」前提。特に「決定は design.md に転記してから再開」「impl.md を書いたら別エージェントでドキュメントレビュー」は、守られたかどうかを外から確認する仕組みが無い

## Docker Sandboxes について調べた事実(D42・D43 の前提)

2026-11-15、docs.docker.com/ai/sandboxes の公式ドキュメントから:
- CLI は `sbx`。Docker Desktop は不要。macOS は Sonoma 14 以降の Apple silicon が条件(この Mac は arm64・macOS 26.6 で条件を満たす。2026-11-15 にユーザーが `sbx` を入れ、VM の中で `/login` 済み)
- VM ごとにファイルシステム・ネットワーク・Docker デーモンを持つ microVM。`sbx rm <名前>` で VM ごと消せる(ホストのファイルは残る)
- 作業場所の渡し方は 3 つ。(1) 直接マウント: 指定したホストのディレクトリが同じ絶対パスで見え、変更は双方向に即時反映される。(2) クローン(`--clone`): ホストのリポジトリを読み取り専用でマウントし、VM の中の非公開クローンで作業する。(3) マウント無し(パスを渡さない `sbx create`。パスを渡せば (1) と同じくマウントする)。**特定のファイルやパスを除く設定は、ドキュメントに見当たらない**
- Claude Code は `sbx run claude <パス> -- "<プロンプト>"` で起動し、既定で `--dangerously-skip-permissions` が付く。`claude -p`(結果を返して終わる使い方)はドキュメントに無いが、`sbx exec` で動くことを 2026-11-15 に試行で確かめた
- 認証: サブスクリプションなら VM の中の Claude Code で `/login`(トークンはホスト側に残り VM には置かれない)。API キーなら `sbx secret set anthropic`。ホストの `~/.claude` は VM の中では使われず、作業ディレクトリの `.claude/` だけが見える(その中のサブエージェント定義・hook が効くかは書かれていないが、`claude --agent kn-implementer` で定義・hook・モデルが効くことを 2026-11-15 に試行で確かめた。ホストの規約スキルは見えない(D47 (a)))
- ネットワーク: 既定の `balanced` はパッケージレジストリなどを許可し、それ以外は承認を求める。npm のレジストリと bun の配布元に届くことを 2026-11-15 に確かめた
