## 受け入れ要件 doc の導入(ユーザー提案、2026-10-18)

### ユーザー案

1. design.md / impl.md に加えて、**受け入れ要件 doc** を作る
2. 実装の前に、受け入れ要件 doc に基づいて **テストを作る工程** を入れる
3. **実装エージェントには受け入れ要件 doc を読ませずに** 実装させる
4. テストが通れば(= 受け入れ要件を満たしていれば)OK とする

### 想定フロー(たたき台)

```
design.md(仕様・要件)
   ↓
メインがユーザーと acceptance.md(受け入れ要件)を作成 → ユーザー承認
   ↓
メインが acceptance.md からテストを書く → 全件 fail(red)を確認
   ↓
実装エージェント(acceptance.md・テストは読まない)が design.md / impl.md を元に実装
   ↓
機械的検証: lint + 受け入れテスト(green になるまで)
   ↓
レビュー → メインがコミット(D9)
```

### 前提として確認できた事実

- このリポジトリには現時点でテストの仕組みが無い(各 `package.json` に test スクリプトが無い)。受け入れテストを回すには、先にテスト基盤を入れる必要がある
- 既存の `kn-implement-review-loop` は「lint + テスト」を機械的検証ゲートにしているが、テスト未整備の場合は記録して skip する設計。受け入れテストを停止条件の中心に置くなら、skip は許されなくなる

## 現状スキルの問題点(洗い出し)

### (a) スキル本文から見つかったもの

**明確な不整合・バグ**

- A1. `kn-code-review-agent` の採点閾値が食い違っている。`SKILL.md` の手順 4 と `rules.md` の全体フローは「80」、`rules.md` の閾値節は「75」
- A2. `commit-workflow-flag.sh` はスキル名が `commit-workflow` / `*:commit-workflow` のときだけフラグを立てる。`kn-commit-workflow` を起動してもフラグが立たず、コミットがゲートで止まる(改修版を運用する上での障害)
- A3. ~~`kn-subagent-orchestration` は「git 書き込みはコミットエージェントに委譲」と定めるが、コミットゲートのフラグはセッション ID 単位。サブエージェントのスキル起動でフラグが立つかは未確認~~ → D9(メインがコミット)で解消

**抜けやすい構造**

- A4. 強制力があるのはコミットゲートだけで、他は全部「読んで守る」前提。特に「決定は design.md に転記してから再開」「impl.md を書いたら別エージェントでドキュメントレビュー」は、守られたかどうかを外から確認する仕組みが無い
- A5. 1 つの手順のルールが 3 ファイルに分散している(例: ドキュメントレビューの起動契機は design-impl-docs、役割は subagent-orchestration、ループ内の位置は implement-review-loop)。どれか 1 つを読み飛ばすと手順が抜ける
- A6. 手順が重い。impl.md 作成 → ドキュメントレビュー → 実装 → lint/テスト → ドキュメントレビュー → 5 レンズ + 指摘ごとの Haiku 採点 → コミットエージェント、を最大 3 周回す。重さそのものが省略の動機になる
- A7. このリポジトリのドキュメント配置(`docs/issues/<番号>-<slug>/`)はスキルの既定(`docs/<feature>/`)と違うが、プロジェクト側にそれを書いた CLAUDE.md が無い
- A8. 機械的検証ゲートの lint / テストコマンドが、このリポジトリでは定まっていない(テスト無し)。ゲートは毎回「未整備で skip」になる

### (b) 過去セッション記録から見つかったもの

2026-10-18 調査。対象は Phase 1〜#20 のセッション(b3ced252、サブエージェント 168 件)が中心。他の 2 セッションはスキル運用前で、該当なし。

**ルール違反・手順抜け**

- B1. **スキルが起動されないまま作業が進んだ。** メインが `subagent-orchestration` を初めて読んだのは #8 着手時で、#6 / #7 / #15 ではメインが直接コミットしていた。`design-impl-docs` はメインでは一度も起動されていない(A4 の実例)
- B2. **#20 の PR レビュー対応(#20 の D23)で、レビューを飛ばした。** メインが自分で差分を確認し、impl.md も直接編集し、ドキュメントレビューもコードレビューも回さずにコミットした。PR レビュー起因の小修正をループに戻すかどうかの基準が無い
- B3. **委譲の境界が曖昧。** デプロイ(cf build / deploy / 検証の curl)と impl.md の記録をメインが直接行った。「小修正は直接やってよい」と「ドキュメント執筆は委譲」のどちらに当たるか判断できない
- B4. **フェーズ配置(cf CLI 移行を Phase 1 / 2 のどちらでやるか)を推測で決めかけた。** ユーザーが「これは決定です」と訂正した
- B5. **サブエージェントが裸の `cd` を使い続けた。** 委譲プロンプトに禁止を書いても 1 体で 26 回使われた。禁止事項が委譲プロンプトの雛形に常設されておらず、毎回手書きになっている
- B6. **dotenv のテンプレートを表示した。** メインの grep とサブエージェントの Read。中身はダミーで実害なし

**hooks で詰まったもの**

- B7. **コミットゲートが、スキル未配置のまま有効になっていた。** hook は「スキルを起動せよ」と要求するが、スキルが存在せず、翌日まで一切コミットできなかった(A2 と同じ種類の問題)
- B8. **Co-Authored-By の扱いが揺れた。** hook の文面に残っていた「フッターを付けない」をスキルの規約と取り違え、後から amend で付け直した。hook の文面は修正済み(`~/skills` f20bfaa)。ただしスキル本文にはフッターについての規定が今も無い
- B9. **secret-file-guard が、パスを文字列として含むだけで止める。** メモ・README・design.md への書き込みや、URL 中の `secrets/` でも止まり、言い換えの試行錯誤が毎回発生した。hook のメッセージに対処の指針が無い
- B10. **gh-write-guard の許可範囲をエージェントが把握できなかった。** その後 `.claude/gh-write-allow.json` で拡張できるようになった。ただし、エージェントがこのファイルを書き換えて自分に権限を与えられるかは未確認

**手順が重すぎた**

- B11. **#20 で 84 体のサブエージェントを起動した**(Haiku 40 / Sonnet 35 / Opus 9)。採点を指摘 1 件ごとに Haiku 1 体で行っており、1 周で 20 体。ドキュメントだけの差分でも 5 レンズ + 採点が走った(A6 の実例)
- B12. **ドキュメントの時制の修正という軽い指摘で、3 周の上限を超えた。** ユーザー判断(#20 の D22)と 1 周の延長が必要になった。上限が指摘の種類を区別していない

### U21. 受け入れテストにできる振る舞いが無いタスクのフロー

- 対象: スキル・hooks・設定・ドキュメントの変更など、アプリの振る舞いが変わらないタスク(このタスク自体もそう)
- 現状のスキルでは、acceptance.md を省けるのは「調査・ドキュメントのみ」のタスクだけ。フローの 1(受け入れ要件)・2(受け入れテスト)・4(kn-implementer による実装)をこの種のタスクで通すのかが決まっていない
- 選択肢
  - (ア) acceptance.md・受け入れテストを省き、**メインが直接実装する**。隠すべき受け入れ要件が無いので、実装を隔離する理由が無い(D7)。コードレビューは kn-code-reviewer に出す(メインが author になるため。D23)。impl.md のドキュメントレビューと理解度チェックは通常どおり
  - (イ) 通常のフローどおり。acceptance.md を書き、確認方法を ②(Claude が確認)中心にして、実装は kn-implementer に出す
  - (ウ) 軽量ルートに乗せる
- トレードオフ: (ア)は委譲が最小で、今回このタスクで実際にやった進め方と同じ。ただし「何ができたら完了か」を文書で固定しない。(イ)は完了条件が明確になるが、隠す意味の無い要件を隠すために委譲が増える。(ウ)は小さな修正向けのルートで、ドキュメントレビュー・理解度チェックまで省いてしまう
- 推奨: (ア)。完了条件は design.md の要件・決定事項で足りる

### U22. コーディング規約スキルの遵守を誰が担保するか

- 対象: ts-type-safety / function-signature-typing / neverthrow-coding-rules などのグローバルのコーディング規約スキル
- 現状: kn-code-review の「指摘しないもの」に「コーディング規約スキルが扱う領域」を入れている(改修前のスキルにもあった除外)。一方 kn-implementer の定義にはこれらのスキルへの言及が無い。スキルは自動で起動する前提だが、起動しなかった場合に誰も確認しない
- 選択肢
  - (ア) kn-implementer の定義に「コーディング規約スキルに従う」と書き、kn-code-reviewer にもこれらの規約違反を確認させる(除外をやめる)
  - (イ) kn-implementer の定義に書くだけで、レビューの除外は残す
  - (ウ) lint のルールで機械的に止める(規約ごとに lint 化できるかの判断が要る。別タスク)
- 推奨: (ア)。B5 で見たとおり、書くだけでは守られないことがある。lint 化(ウ)は将来の改善として別に検討する
