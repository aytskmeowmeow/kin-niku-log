## 受け入れ要件 doc の導入(ユーザー提案、2026-10-18)

### ユーザー案

1. design.md / impl.md に加えて、**受け入れ要件 doc** を作る
2. 実装の前に、受け入れ要件 doc に基づいて **テストを作る工程** を入れる
3. **実装エージェントには受け入れ要件 doc を読ませずに** 実装させる
4. テストが通れば(= 受け入れ要件を満たしていれば)OK とする

### 想定フロー(たたき台)

```
design.md(仕様・要件)
   ↓
メインがユーザーと acceptance.md(受け入れ要件)を作成 → ユーザー承認
   ↓
メインが acceptance.md からテストを書く → 全件 fail(red)を確認
   ↓
実装エージェント(acceptance.md・テストは読まない)が design.md / impl.md を元に実装
   ↓
機械的検証: lint + 受け入れテスト(green になるまで)
   ↓
レビュー → メインがコミット(D9)
```

### 前提として確認できた事実

- このリポジトリには現時点でテストの仕組みが無い(各 `package.json` に test スクリプトが無い)。受け入れテストを回すには、先にテスト基盤を入れる必要がある
- 既存の `kn-implement-review-loop` は「lint + テスト」を機械的検証ゲートにしているが、テスト未整備の場合は記録して skip する設計。受け入れテストを停止条件の中心に置くなら、skip は許されなくなる

### U28. `apps/*` の下にある設定ファイルは運用ルートの「設定」か

最終のドキュメントレビュー・コードレビューで出た疑問。D34 は「アプリのコード(`apps/`・`packages/` のソース)は対象外、`packages/eslint-config/`・`packages/typescript-config/` は設定」と決めたが、`apps/{api,web}/` の直下にある `tsconfig.json`・`eslint.config.js`・`package.json`・`vite.config.ts`・`cloudflare.config.ts` がどちらかは決まっていない。vite・cloudflare の設定はビルド・デプロイを通してアプリの振る舞いを変えうる。

- (ア) `apps/*` の設定ファイルもすべて運用ルートの対象にする
- (イ) `apps/` の下はすべて対象外(通常フローか軽量ルート)にする
- (ウ) tsconfig・eslint の設定・package.json の scripts だけを対象にし、ビルド・デプロイの設定(vite・cloudflare)は対象外にする
- トレードオフ: (ア) は判定が単純だが、ビルド・デプロイの変更が受け入れ要件なしで入る。(イ) は安全側だが、lint・型の設定変更のたびに kn-implementer を通す。(ウ) は D34 の「共有の lint・TS 設定は設定」と同じ線引きを `apps/` にも当てる
- 推奨: (ウ)。スキルは今「`apps/`・`packages/` のソース」と D34 の文言どおりに書いてあり、設定ファイルの扱いは書いていない

### U29. 通常フローのタスクで出た、アプリのコードに触れない小さな修正の行き先
