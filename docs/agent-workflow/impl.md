## 新しいフロー(全体像)

D7〜D35・D37〜D40・D42〜D48 を 1 本の流れにしたもの。スキル本文はこの流れを正として書く。

```
0. 開始      docs/issues/<番号>-<slug>/ を作る。design.md をユーザーと作る
             外から見た契約(API は openapi.yaml、画面の操作)をここで決める(D16 の前提)
1. 受け入れ   メインがユーザーとの会話から acceptance.md を起案する(D8)
             各要件に確認方法 ①自動テスト ②Claude が localhost で確認 ③ユーザーの手動確認 を付ける(D13)
             → ドキュメントレビュー(kn-doc-reviewer): design.md の機能要件・非機能要件を漏れなく網羅しているか(D12)
             → ユーザーが「承認済み」にする(D15)
2. 受け入れテスト  メインが ① を書く(D16)。全件 red を確認し、実装の前にコミットする。このコミットに design.md と acceptance.md も含める
             ※テスト基盤は Phase 3 から(D14)
3. 方針      メインが impl.md を書く
             → ドキュメントレビュー(kn-doc-reviewer): design.md ↔ impl.md
             → レビューを反映したら impl.md をコミットする
4. 実装      kn-implementer。Docker Sandboxes の VM の中で、受け入れ要件を除いた作業場所だけを渡して動かす(`kn-sandbox.sh`、D42〜D48)。タスク文書で読むのは design.md / impl.md だけ(D8・D17)。コーディング規約スキルに従う(D31)
             単体テストは自由に書く(D16)。impl.md は書かず、成果(変更ファイル・判断・疑問)をメインに報告する(D29)
             テストや仕様の誤りに気づいたら、仕様の言葉で疑問としてメインに返す(D16)
             → メインがテストを直すか、design.md の未決事項に上げる
5. 検証      メインが lint / check-types / 単体テスト / 受け入れテスト ① を実行し、② を localhost + ブラウザで確認する
             ① ② の未達は、メインが「どの要件が未達か」を design.md の言葉に言い換えて 4 に戻す(D11)
6. レビュー   kn-code-reviewer(サブエージェント 1 体)がコードをレビューする(D23)。観点は kn-code-review の 6 観点(D31 のコーディング規約を含む)
             指摘は、メインが design.md の言葉に言い換えて 4 に戻す。impl.md・design.md に記録するときも言い換える(D47 (e)・D48 (d))(受け入れ要件・テストの中身を実装エージェントに渡さないため。D8・D11)
             仕様に関わる指摘は design.md の未決事項へ
             レビュアーが挙げた lint 化の候補は、impl.md の「レビュー指摘と対応」に、レビュー回ごとに `- lint 化の候補: …` の 1 行で記録する(D31・D35)。PR の前にメインが `git grep` で候補を集めてユーザーに報告する(D35)
7. コミット   メインが kn-commit-workflow でコミットする。承認は取らない(D9)
8. 動作確認   ③ をユーザーに依頼する(D13)
9. 理解度チェック  issue(issue にしないタスクではタスク。D32 (d))ごとに 1 回(D19)。結果は push の前にコミットする
             メインが差分と design.md から 3〜5 問出す。観点: なぜこの設計か / 異常系 / 影響範囲 / どこを見れば挙動が分かるか(D20)
             ユーザーが説明できるまで解説と再質問を続ける。説明できたら、ユーザーが「このまま進む / 改善を提案」を決める(D21)
             改善の提案は軽量ルートで対応する(D27)。アプリのコード・振る舞いに触れないものは「運用ルートの小さな修正」で対応する(D33・D38)。仕様の変更を伴うものは元のタスクのフローに戻す(D39 (a)・D40 (c))。Claude はチェックの結果から独断で書き換えない(D21)
             結果は impl.md の「理解度チェック」節に残す(D22)
10. PR 作成  PR の前に、メインが `git grep` で各タスクの impl.md から lint 化の候補を集め、件数と中身をユーザーに報告する(D35)。push は push 確認 hook でユーザーが承認する
```

### impl.md の更新とドキュメントレビュー

メインが impl.md を更新したときにドキュメントレビューを走らせる契機は、旧 `kn-design-impl-docs` の「中核ルール」節の表を元に、`kn-task-docs` の「ドキュメントレビューの契機」に置いた(acceptance.md の行、表記修正の行、軽量ルート・運用ルートの小さな修正の行を追加)。

- 走らせる: 初版の作成時 / 「構成」「技術的判断」への書き込み / design.md の変更直後の更新
- 走らせない: 「実装状況」の更新だけ / 「レビュー指摘と対応」「理解度チェック」への追記だけ / 軽量ルート・運用ルートの小さな修正での更新(D27・D33)
- D28 の「表記・時制の修正はメインがその場で直す」は、この「走らせない」側の扱いに揃える(方針を動かさない修正はレビューしない)

### 軽量ルート(D27)

PR レビュー対応や理解度チェック後の改善提案など、仕様の変更を伴わず、アプリのコード・振る舞いに触れる小さな修正(B2・D38)。仕様の変更を伴わず、アプリのコード・振る舞いに触れない小さな修正は、タスクの種類を問わず「運用ルートの小さな修正」で扱う(D33・D38)。

```
メインが軽量ルートに乗せると判断し、impl.md に 1 行残す
→ kn-implementer が修正(隔離を保つため、メインは書かない)
→ 検証(5 と同じ)
→ kn-code-reviewer がレビュー(D23)
→ コミット
→ push(既存の PR がある場合。push 確認 hook でユーザーが承認する)
```

- 省くのはドキュメントレビューと理解度チェック(D27)
- ③ の動作確認は、修正が ③ の要件に関わる場合だけ依頼する
- 仕様に触れると分かった時点で通常ルートに戻す

### 運用ルート(D30)

新しく始めるタスクのうち、スキル・hooks・設定・ドキュメントだけを変え、アプリのコード・振る舞いに触れないもの(D30 の列挙。このタスク自身もここに当たる)。既存タスクの中で出た修正は、軽量ルートか運用ルートの小さな修正で扱う(コードレビュー第 5 回 #1・#2 の重なりを解消するため、スキルで対象を新しいタスクに限った)。判断の基準は「アプリのコード・振る舞いに触れるか」で、ファイルの場所ではなく変更の内容で決める(D37)。スキルには例を並べ、ここに無いものも同じ基準で判断すると書く。軽量ルートと運用ルートの小さな修正も、この基準と例で振り分ける(D38)。

- 運用ルートで扱うもの: スキル・hook・ドキュメントの変更。設定のうち、アプリの振る舞いが変わらないことを lint / check-types / build / テストで確かめられる変更(lint・型の設定、package.json の scripts など。共有の `packages/eslint-config/`・`packages/typescript-config/` を含み(D34)、`apps/*` の下の設定ファイルも内容で判断する(D37))
- 通常フロー(小さな修正なら軽量ルート)で扱うもの: アプリのソース(`apps/`・`packages/` のソース)の変更(リファクタリングを含む。D34)、依存ライブラリの更新(バージョンの上げ下げすべて)、ビルド・デプロイ・コード生成の設定(vite・cloudflare・drizzle・orval など)の変更(D37)、DB のマイグレーション・静的ファイル(`index.html`・`public/`)の変更(D40 (d))
- テストコード: 単体テストはアプリのソースとして扱う(小さな修正なら軽量ルート。D40 (b))。受け入れテストだけの修正は `apps/` の下にあってもアプリのコードとして扱わない(D39 (b))
- 迷う例: tsconfig のうちビルドの出力にも効く設定(`jsx`・`useDefineForClassFields` など)(D39 (c))
- 振る舞いに影響するか迷ったら、ルートを選ぶ前に理由を添えてユーザーに聞く(D37)

```
0. 開始(design.md。issue にしないタスクは `docs/<slug>/`)→ 3. 方針(impl.md、ドキュメントレビューあり)
→ メインが直接実装 → 検証(対象に合わせる。hook ならテストケースを流す)
→ kn-code-reviewer がレビュー → コミット(8 は省く。D32 (a))→ 理解度チェック → PR
```

- 省くのは受け入れ要件・受け入れテスト。隠す受け入れ要件が無いので、実装は委譲しない(D7)。③ の動作確認は acceptance.md の区分なので、運用ルートには出てこない。ユーザーの環境でしか確かめられない確認(グローバル設定の変更など)が要るときは、impl.md の検証方法に「ユーザーに確認を依頼」と書き、コミット後に依頼する(D32 (a))
- メインが author になるので、コードレビューは必ず kn-code-reviewer に出す
- 周回の上限も適用する。数えるのはメインの実装が戻った回数(D32 (b))
- 検証の方法は impl.md に残す(テスト基盤の対象外なので、何で確かめたかを書かないと追えない)。リポジトリの設定・ツール設定かテストコードに触れる場合は lint / check-types / build も実行する(D32 (e))。テスト基盤が入った後(Phase 3 から)は、触れた範囲によらず単体テスト・受け入れテストを毎回実行する(D37 の「テストで確かめられる」に合わせる)
- 完了条件は design.md の要件・決定事項(D30)。kn-code-reviewer には acceptance.md が無いことを伝え、design.md と照合させる。kn-code-review の観点 1 にもそう書いてある
- 検証の未達・レビューの指摘で戻るときは、メインが直接直す(実装エージェントへの言い換えは要らない)。進行報告の「lint / テスト / ② の結果」は、impl.md に残した検証方法の結果に置き換える(レビュー指摘の件数はそのまま報告する)
- 3 でレビューを反映したら design.md と impl.md をコミットする(通常フローでは design.md を 2 でコミットするが、運用ルートは 2 を省くため)(D32 (e))
- 理解度チェックは、issue にしないタスクではタスクごとに 1 回(D32 (d))
- 仕様の変更を伴わず、アプリのコード・振る舞いに触れない小さな修正(理解度チェック後の改善提案、PR レビュー対応)は、タスクの種類(通常フロー・運用ルート)を問わず「運用ルートの小さな修正」で扱う(D33・D38)。受け入れテストだけの修正(acceptance.md を変えないもの)もここに入る。acceptance.md を変えるなら仕様の変更として扱い、元のタスクのフローに移す(D39 (a)・(b))。design.md の修正は、要件・仕様・決定事項の中身を変えるなら仕様の変更、古い記述の更新・転記漏れ・表記は小さな修正(D40 (c))。スキルの実行手順 3 では、既存タスクの中の修正を先に見て、新しいタスク(運用ルート / 通常フロー)と分ける。メインが直し、kn-code-reviewer のレビューだけ通す(通常フローのタスクなら acceptance.md も渡す)。ドキュメントレビューと理解度チェックは省く(D33)。検証・コミット・push と周回の上限は運用ルート・軽量ルートと同じ扱い(D9・D28)。アプリのコード・振る舞いに触れると分かった時点で軽量ルートに移す。仕様に触れると分かった時点で元のタスクのフローに移し、アプリのコード・振る舞いにも触れるなら通常フローに移す(D39 (a))
- アプリのコード・振る舞いに触れる(対象の定義で通常フローに当たる)と分かった時点で、通常のフロー(小さな修正なら軽量ルート)に戻す(D32 (c)・D34・D37)

### 周回の上限(D28)

- 実装の不備で 4 に戻った回数を数え、上限 3 回。検証(5)の未達で戻った場合と、レビュー(6)の指摘で戻った場合の両方を数える。D28 の「コードへの指摘」を、ユーザーの補足「実装が困難な場合に止まるためのもの」に沿って解釈した
- 軽量ルート・運用ルートにも適用する。運用ルートではメインの実装が戻った回数を数える(D32 (b))。運用ルートの小さな修正(D33・D38。通常フローのタスクから出たものを含む)にも適用する
- 仕様を新しく決めたら、その反映は新しい実装として 0 から数え直す(D40 (a))
- 数えないもの: ドキュメントの表記・時制などの修正(メインがその場で直す)、テストや仕様の誤りによる戻り(4 の疑問経路。実装の不備ではない)
- 上限に達したら design.md の未決事項に状況・選択肢・推奨を書いて止める(現行と同じ)

### Phase 3 までの検証ゲート(A8)

- 通常フロー・軽量ルートでは、テスト基盤が入るまで(D14)は、検証を `bun run lint` / `bun run check-types` / `bun run build` で行う(#20 と同じ)
- テストを省いたことは impl.md に記録する(現行のルールを維持)

### kn-implementer を VM で動かす(第 8 版、D42〜D48)

`.claude/scripts/kn-sandbox.sh <サブコマンド> <タスク>`。VM の名前は `kn-<タスク>`。置き場所は `~/.cache/kn-sandbox/<タスク>/`(D45)で、作業場所(VM にマウントする)は `ws/`、委譲プロンプトは `prompt.md`。

| サブコマンド | 内容 |
|---|---|
| create | VM を作り(D47 (b))、package.json の `packageManager` の版の bun を入れ(D44 (a))、その VM だけ GitHub への通信を止める(D47 (f)。bun の配布元が GitHub なので、入れた後で止める)。途中で失敗したら VM を消す。最後まで済んだ印を置き場所に残し、run はその印を確かめる |
| recreate | 壊れた VM だけを消して create し直す。置き場所(取り込んだファイルの記録など)は残す(D48 (a)) |
| prepare | 今の作業ツリー(add 済みで未コミットのファイルを含む)を、元のリポジトリの index を変えずに書き出す(D46)。受け入れ要件を大文字小文字を問わず除き、`.claude/hooks/` は残す(D44 (b))。未追跡の新しいファイルのうち、パスのどこかの要素が「.」で始まるものは、collect が取り込んだもの以外を除く(D47 (c)・D48 (c))。一覧のファイルにある規約スキルの `SKILL.md` と `references/` を作業場所の `.claude/skills/` に写す(D47 (a)・D49)。見つからなければ止まる。取り込んでいない kn-implementer の変更が作業場所にあれば止まる(`--force` で捨てる) |
| run | 作業場所で `bun install` を走らせ、VM の中で `claude --agent kn-implementer -p` を動かす。`--continue` で同じ VM の直前の会話を続ける(D29 の「使い続ける」の代わり。SendMessage は使えない) |
| collect | 作業場所の差分を元の作業ツリーに取り込む。取り込めないパス(D47 (d)・D48 (e))かシンボリックリンク(D48 (f))に触れる差分が 1 つでもあれば、何も取り込まない。元の作業ツリーに当てられない(メインが同じ箇所を変えた、など)ときも、何も取り込まない(仮決定 P1)。取り込んだら、その状態を差分の起点(base)にし、取り込んだ新しいファイルを記録する |
| rm | VM と置き場所を消す(PR のマージ後) |

- 標準出力は kn-implementer の報告だけにし、bun や sbx の出力は標準エラーに出す
- `sbx` は `--no-input` で動かす。承認を求められる場面では、止まらずに失敗させる
- 写す規約スキルは、一覧のファイル `.claude/scripts/kn-sandbox-skills.txt`(1 行に 1 つ)から読む(D49)。規約スキルを増やすときは、この一覧に 1 行足すだけでよい。kn-implementer.md にはスキルの名前を書かない
- 新しく作った VM でも `/login` はやり直さなくてよい(ユーザーが最初の VM で一度ログインした後、試験で作り直した VM でもそのまま動いた)

### プロジェクトの CLAUDE.md(新規、リポジトリのルート)

スキルが読まれずに作業が進んだ(B1)対策。CLAUDE.md は毎セッション必ず読み込まれるので、ここに入口を置く。

- 開発タスクは `kn-dev-workflow` に従う。グローバルの元スキル(`subagent-orchestration` / `implement-review-loop` など)は使わない
- タスクのドキュメントは `docs/issues/<番号>-<slug>/`。issue にしないタスク(このタスクのような、エージェント運用など)は `docs/<slug>/` に置く(このタスクで既に採っている配置を明文化するもの)
- 書く内容は入口だけにし、ルール本体はスキルに置く(二重管理を避ける)
- 第 8 版で、kn-implementer の行を「VM の中で動かし、受け入れ要件を除いた作業場所だけを渡す。Agent ツールでは起動しない」に書き換えた(D42)

## 技術的判断

- **acceptance.md の網羅(D12)は、ドキュメントレビューで担保する。** メインが起案した acceptance.md を、別エージェントが design.md の要件と突き合わせる。D12 は手段を決めていないので、既にある reviewer != author の仕組みを使う
- **受け入れテストは実装の前にコミットする。** red の状態をコミットに残し、実装前後の差分で「テストを変えずに通した」ことを確かめられるようにする。そのため acceptance ガードは git の履歴も塞ぐ
- **コードレビューの観点は残し、実行の仕組みを 1 体にまとめる**(D23)。5 レンズの観点(仕様遵守 / impl.md との整合 / バグ・エッジケース / デグレ / 可読性)は有用だったので、コーディング規約(D31)を加えた 6 観点を、チェックリストとして kn-code-reviewer に全部見させる
- **kn-code-reviewer は acceptance.md を読んでよい。** 隔離の対象は実装エージェントだけ(D8・D17)。レビュアーが受け入れ要件を知っていると要件の抜けに気づける。中身が実装エージェントに漏れないよう、指摘はメインが言い換えてから渡す(フローの 6)
- **受け入れテストの置き場所の規約は「パスに `acceptance` を含む」とする。** 具体的な場所は Phase 3 で決める(D14)が、VM の作業場所からの除外(第 8 版)とガードが判定できる条件を、ここで先に決めておく。場所の選択肢を狭めるのは、ディレクトリ名かファイル名に `acceptance` を入れることだけ
- **レビュー用のエージェントは毎回新しく起動する。** 前回の指摘に引きずられずに見させるため。D29 で使い続けるのは実装エージェントだけ
- **差分を取るための git は、VM にマウントする作業場所の外(`<タスク>/git`)に置く。** 作業場所の中の `.git` は VM から書き換えられ、ホストの git がその設定(フィルタ・外部の diff・fsmonitor など)に従うと、ホストでコマンドが動きうる(コードレビュー第 7 回 #2)。作業場所の中の `.git` は、kn-implementer が VM の中で差分を見るためだけに、VM の中で作る(ホストの git では触らない)。作業場所の `.gitattributes` は、差分用の git の `info/attributes` で打ち消す。ホストが作業場所を書き換える・読む間(prepare・collect)は VM を止め、VM の中に残ったプロセスと競合させない(コードレビュー第 8 回 #5・#9。VM を止めるのは仮決定 P4)。取り込んだら、その状態を差分の起点にする(続けて取り込むときに増えた分だけを当てる。第 8 回 #1・#2)。差分は plumbing の `diff-index`(リネームを検出しない)で取り、ホストの diff の設定の影響を受けないようにする
- **作業場所を置き場所の直下ではなく `ws/` にする。** 差分用の git・記録(差分の起点 base、取り込んだファイルの一覧、create が済んだ印、直近のパッチ)・委譲プロンプトを、マウントの外に置くため
- **VM は `sbx run` ではなく `sbx create` + `sbx exec` で動かす**(D47 (b))。`sbx run` は対話の無い環境では `--detach` 無しだと拒まれる。`sbx run` が既定で付ける `--dangerously-skip-permissions` は、run で明示して付ける。VM は使い捨てで、acceptance ガードの hook はこの指定でも止める(第 8 版の試行で確かめた)
- **node_modules は委譲のたびに作り直す。** prepare は作業場所の中身を入れ替えるので、run で毎回 `bun install` を走らせる。VM の中の bun のキャッシュはタスクの間残るので短く済む(D43 (c) の理由の意味)

## 既知の制約

- **Bash を完全には塞げない。** 変数展開・別名・スクリプト経由の読み込みは、コマンド文字列からは判定できない。hook は「普通にやると読めない」水準を目標にし、エージェント定義の本文の禁止事項と二重にする。第 8 版からは、受け入れ要件を VM に渡さないこと(D42)が主な層で、hook は安全網になった
- **acceptance ガードは Phase 3 まで実地で試せない**(D14)。それまでは、hook 単体に JSON を流して判定を確かめるところまで。VM の中で Read を止めることは第 8 版で確かめた。受け入れテストがある状態での判定は Phase 3 で確かめる
- **コミットゲートの修正(A2、D24)が入るまで、`kn-commit-workflow` ではコミットできない。** それまでのコミット(分割案の 1・2 など)はグローバルの `commit-workflow` を起動して行う
- **スキル未配置のままコミットゲートが有効になる問題(B7)は、今回の修正では対処しない。** D24 で判定するスキル名を広げるだけで、「スキルが存在しない」場合の案内は足さない。このリポジトリでは kn- 版がリポジトリ内にあるので起きない
- **「決定を design.md に転記したか」「ドキュメントレビューを走らせたか」を外から確かめる仕組みは作らない(A4、見送り)。** 転記の有無はファイルの中身の判断で、hook では判定できない。代わりに、CLAUDE.md で入口を固定し(B1)、手順を減らして省略の動機を減らす(A6)
- **見送り(D26):** サブエージェントの裸の `cd` を止める hook(B5。エージェント定義の本文に禁止事項を常設して対処)、dotenv テンプレートの表示(B6。閲覧可の判断済みで実害なし)
- **D31 の lint 化は別タスク。** それまでは、規約スキルの遵守を kn-implementer の定義(従うと明記)とコードレビューの 6 つ目の観点だけで担保する
- **差分の外の気づき(このタスクでは直さない):** kn-commit-workflow の push の例外が「PR 作成時の push」だけで、軽量ルート・運用ルートの小さな修正の push に触れていない。kn-dev-workflow の 2 で受け入れテストと文書を 1 コミットにする記述が、kn-commit-workflow の意味単位の分割とぶつかる
- **kn-code-reviewer の tools のうち Grep・Glob が使えない。** 最終レビューで、Skill は使えたが Grep・Glob は無かった(frontmatter には書いてある)。glob メタ文字を含むパスが出てくる Phase 3 で検索に困る可能性がある。原因は未調査
- **見送り:** 最終コードレビュー #7(軽量ルート・運用ルートの小さな修正の周回を、元のタスクから引き継ぐか 0 から数えるか)。D28 の解釈に関わるが、小さな修正で上限に達することは稀なので、実際に起きたときに判断する。D38 で通常フローのタスクから出た小さな修正も対象に入った
- **振り分けの整理(別タスク、D41):** 次の論点は決めずに残す。(1) 既存タスクの「小さくない」修正(仕様は変えない)の行き先。(2) 新しく起こす小さなタスク(1 行のバグ修正 issue など)を軽量ルートに乗せるか。スキルの対象の定義(「小さな修正なら軽量ルート」)と実行手順 3(新しいタスクは運用ルートか通常フロー)で読み方が割れる。(3) 1 件の修正がアプリのコードと受け入れテストの両方に触れる場合。(4) D40 の反映後の周回の数え方(D40 自体も新しい決定にあたるか)。(5) 通常フローの 4〜6 の途中で見つかった受け入れテストの誤りに D39 (b) を当てるか(4 の「メインが直す」と、小さな修正としてレビュー・コミットを別に回すかで読み方が割れる。メインが一度「7 の後に限る」と書いたが、D39 (b) に無い限定なので取り消した)。(6) 運用ルートの小さな修正で design.md と impl.md を直すとき、kn-task-docs の契機の表で「design.md の変更直後の更新 → 必須」と「小さな修正での更新 → 不要」が同時に当たる。(7) 実行手順 3 の「既存タスクの中で出た修正」の範囲(8 の動作確認で出た修正、7 の後にユーザーが直接頼んだ修正)。別タスクでは、ルートの数や振り分けの軸を減らす見直しも検討する

- **VM 化(第 8 版)の制約:**
  - 受け入れテストがまだ無いので、本物の受け入れ要件を除けるかは Phase 3 の実走で確かめる(除外の判定は試験ファイルで確かめた)
  - VM が隠せるのは kn-implementer が自分で読む経路だけ。メインが差し戻しで中身を伝える経路は、引き続き「実装エージェントへの戻し方」の「渡さないもの」が担う。impl.md・design.md に記録するレビュー指摘も同じく言い換える(D47 (e)・D48 (d))
  - `run` は kn-implementer の作業が終わるまで返らない。Bash の上限(10 分)を超えうるので、バックグラウンドで動かす
  - prepare は作業場所の中と置き場所の差分用の git で `git commit` を実行する。使い捨ての git で、元のリポジトリの履歴には入らないが、コミットゲートの hook はスクリプトの中のコマンドを見ない
  - ネットワークのポリシーが承認を求める通信は、`--no-input` で失敗する。bun のレジストリと配布元に届くことは確かめた。GitHub は VM ごとに止めている(D47 (f))
  - ホストの `~/.claude` は VM の中では使われないので、グローバルの hook(secret-file-guard・gh の許可リスト保護・force push ブロック・コミットゲート)とグローバルの CLAUDE.md は、VM の中の kn-implementer には効かない。禁止事項はエージェント定義の本文の常設(B5)が担う。dotenv 系は書き出されず、作業場所の git にはリモートが無いので、実害は小さい
  - gitignore の対象でない未追跡ファイルは書き出される。Phase 3 でメインが受け入れテストを走らせると、そのレポート(例: Playwright の `test-results/`)がパスに `acceptance` を含まずに残り、次の prepare で VM に渡りうる。Phase 3 でテスト基盤を入れるときに、出力先を .gitignore に入れるか、パスに `acceptance` を含める(コードレビュー第 7 回 #12)
  - GitHub 以外のミラー・CDN から公開リポジトリの受け入れテストを取りに行く経路は塞いでいない(D48 (g))。わざと取りに行く操作が要る
  - パスの途中に「.」で始まるディレクトリがある未追跡ファイル(`.github/` の下の新しいファイルなど)は、コミットするまで VM に渡らない(D48 (c)。受け入れたのは仮決定 P2)。メインが作ったものを kn-implementer に見せたいときは、先にコミットする
  - VM の中の会話(`--continue`)は recreate で消える
