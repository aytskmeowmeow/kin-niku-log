## 新しいフロー(全体像)

D7〜D35 を 1 本の流れにしたもの。スキル本文はこの流れを正として書く。

```
0. 開始      docs/issues/<番号>-<slug>/ を作る。design.md をユーザーと作る
             外から見た契約(API は openapi.yaml、画面の操作)をここで決める(D16 の前提)
1. 受け入れ   メインがユーザーとの会話から acceptance.md を起案する(D8)
             各要件に確認方法 ①自動テスト ②Claude が localhost で確認 ③ユーザーの手動確認 を付ける(D13)
             → ドキュメントレビュー(kn-doc-reviewer): design.md の機能要件・非機能要件を漏れなく網羅しているか(D12)
             → ユーザーが「承認済み」にする(D15)
2. 受け入れテスト  メインが ① を書く(D16)。全件 red を確認し、実装の前にコミットする。このコミットに design.md と acceptance.md も含める
             ※テスト基盤は Phase 3 から(D14)
3. 方針      メインが impl.md を書く
             → ドキュメントレビュー(kn-doc-reviewer): design.md ↔ impl.md
             → レビューを反映したら impl.md をコミットする
4. 実装      kn-implementer(サブエージェント)。タスク文書で読むのは design.md / impl.md だけ(D8・D17)。コーディング規約スキルに従う(D31)
             単体テストは自由に書く(D16)。impl.md は書かず、成果(変更ファイル・判断・疑問)をメインに報告する(D29)
             テストや仕様の誤りに気づいたら、仕様の言葉で疑問としてメインに返す(D16)
             → メインがテストを直すか、design.md の未決事項に上げる
5. 検証      メインが lint / check-types / 単体テスト / 受け入れテスト ① を実行し、② を localhost + ブラウザで確認する
             ① ② の未達は、メインが「どの要件が未達か」を design.md の言葉に言い換えて 4 に戻す(D11)
6. レビュー   kn-code-reviewer(サブエージェント 1 体)がコードをレビューする(D23)。観点は kn-code-review の 6 観点(D31 のコーディング規約を含む)
             指摘は、メインが design.md の言葉に言い換えて 4 に戻す(受け入れ要件・テストの中身を実装エージェントに渡さないため。D8・D11)
             仕様に関わる指摘は design.md の未決事項へ
             レビュアーが挙げた lint 化の候補は、impl.md の「レビュー指摘と対応」に、レビュー回ごとに `- lint 化の候補: …` の 1 行で記録する(D31・D35)。PR の前にメインが `git grep` で候補を集めてユーザーに報告する(D35)
7. コミット   メインが kn-commit-workflow でコミットする。承認は取らない(D9)
8. 動作確認   ③ をユーザーに依頼する(D13)
9. 理解度チェック  issue(issue にしないタスクではタスク。D32 (d))ごとに 1 回(D19)。結果は push の前にコミットする
             メインが差分と design.md から 3〜5 問出す。観点: なぜこの設計か / 異常系 / 影響範囲 / どこを見れば挙動が分かるか(D20)
             ユーザーが説明できるまで解説と再質問を続ける。説明できたら、ユーザーが「このまま進む / 改善を提案」を決める(D21)
             改善の提案は軽量ルートで対応する(D27)。運用ルートのタスクでは「運用ルートの小さな修正」で対応する(D33)。Claude はチェックの結果から独断で書き換えない(D21)
             結果は impl.md の「理解度チェック」節に残す(D22)
10. PR 作成  PR の前に、メインが `git grep` で各タスクの impl.md から lint 化の候補を集め、件数と中身をユーザーに報告する(D35)。push は push 確認 hook でユーザーが承認する
```

### impl.md の更新とドキュメントレビュー

メインが impl.md を更新したときにドキュメントレビューを走らせる契機は、旧 `kn-design-impl-docs` の「中核ルール」節の表を元に、`kn-task-docs` の「ドキュメントレビューの契機」に置いた(acceptance.md の行と、表記修正の行を追加)。

- 走らせる: 初版の作成時 / 「構成」「技術的判断」への書き込み / design.md の変更直後の更新
- 走らせない: 「実装状況」の更新だけ / 「レビュー指摘と対応」「理解度チェック」への追記だけ
- D28 の「表記・時制の修正はメインがその場で直す」は、この「走らせない」側の扱いに揃える(方針を動かさない修正はレビューしない)

### 軽量ルート(D27)

PR レビュー対応や理解度チェック後の改善提案など、仕様の変更を伴わず、アプリのコードに触れる小さな修正(B2)。運用ルートのタスクの小さな修正は「運用ルートの小さな修正」で扱う(D33)。

```
メインが軽量ルートに乗せると判断し、impl.md に 1 行残す
→ kn-implementer が修正(隔離を保つため、メインは書かない)
→ 検証(5 と同じ)
→ kn-code-reviewer がレビュー(D23)
→ コミット
→ push(既存の PR がある場合。push 確認 hook でユーザーが承認する)
```

- 省くのはドキュメントレビューと理解度チェック(D27)
- ③ の動作確認は、修正が ③ の要件に関わる場合だけ依頼する
- 仕様に触れると分かった時点で通常ルートに戻す

### 運用ルート(D30)

スキル・hooks・設定・ドキュメントだけを変えるタスク(D30 の列挙。このタスク自身もここに当たる)。共有の lint・TS 設定(`packages/eslint-config/`・`packages/typescript-config/`)は設定に含む。アプリのソース(`apps/`・`packages/` のソース。上の 2 つを除く)に触れるタスクは、リファクタリングでも対象外とし、通常フローか軽量ルートで進める(D34)。`apps/*` の下の設定ファイルの扱いは design.md の U28 で確認中。

```
0. 開始(design.md。issue にしないタスクは `docs/<slug>/`)→ 3. 方針(impl.md、ドキュメントレビューあり)
→ メインが直接実装 → 検証(対象に合わせる。hook ならテストケースを流す)
→ kn-code-reviewer がレビュー → コミット(8 は省く。D32 (a))→ 理解度チェック → PR
```

- 省くのは受け入れ要件・受け入れテスト。隠す受け入れ要件が無いので、実装は委譲しない(D7)。③ の動作確認は acceptance.md の区分なので、運用ルートには出てこない。ユーザーの環境でしか確かめられない確認(グローバル設定の変更など)が要るときは、impl.md の検証方法に「ユーザーに確認を依頼」と書き、コミット後に依頼する(D32 (a))
- メインが author になるので、コードレビューは必ず kn-code-reviewer に出す
- 周回の上限も適用する。数えるのはメインの実装が戻った回数(D32 (b))
- 検証の方法は impl.md に残す(テスト基盤の対象外なので、何で確かめたかを書かないと追えない)。リポジトリの設定・ツール設定に触れる場合は lint / check-types / build も実行する(D32 (e))
- 完了条件は design.md の要件・決定事項(D30)。kn-code-reviewer には acceptance.md が無いことを伝え、design.md と照合させる。kn-code-review の観点 1 にもそう書いてある
- 検証の未達・レビューの指摘で戻るときは、メインが直接直す(実装エージェントへの言い換えは要らない)。進行報告の「lint / テスト / ② の結果」は、impl.md に残した検証方法の結果に置き換える(レビュー指摘の件数はそのまま報告する)
- 3 でレビューを反映したら design.md と impl.md をコミットする(通常フローでは design.md を 2 でコミットするが、運用ルートは 2 を省くため)(D32 (e))
- 理解度チェックは、issue にしないタスクではタスクごとに 1 回(D32 (d))
- 運用ルートのタスクで出た小さな修正(理解度チェック後の改善提案、PR レビュー対応)は「運用ルートの小さな修正」で扱う。メインが直し、kn-code-reviewer のレビューだけ通す。ドキュメントレビューと理解度チェックは省く(D33)。検証・コミット・push と周回の上限は運用ルート・軽量ルートと同じ扱い(D9・D28)。アプリのソースに触れると分かった時点で軽量ルートに移す。通常フローのタスクで出た、アプリのコードに触れない小さな修正の行き先は design.md の U29 で確認中
- アプリのソースに触れる、またはアプリの振る舞いに触れると分かった時点で、通常のフロー(小さな修正なら軽量ルート)に戻す(D32 (c)・D34)

### 周回の上限(D28)

- 実装の不備で 4 に戻った回数を数え、上限 3 回。検証(5)の未達で戻った場合と、レビュー(6)の指摘で戻った場合の両方を数える。D28 の「コードへの指摘」を、ユーザーの補足「実装が困難な場合に止まるためのもの」に沿って解釈した
- 軽量ルート・運用ルートにも適用する。運用ルートではメインの実装が戻った回数を数える(D32 (b))。運用ルートの小さな修正(D33)にも適用する
- 数えないもの: ドキュメントの表記・時制などの修正(メインがその場で直す)、テストや仕様の誤りによる戻り(4 の疑問経路。実装の不備ではない)
- 上限に達したら design.md の未決事項に状況・選択肢・推奨を書いて止める(現行と同じ)

### Phase 3 までの検証ゲート(A8)

- 通常フロー・軽量ルートでは、テスト基盤が入るまで(D14)は、検証を `bun run lint` / `bun run check-types` / `bun run build` で行う(#20 と同じ)
- テストを省いたことは impl.md に記録する(現行のルールを維持)

- チャットで受けた決定を、作業再開前に design.md に転記する規律
- reviewer != author

### エージェント定義(`.claude/agents/`)

| ファイル | 役割 | モデル | 使い方 |
|---|---|---|---|
| `kn-implementer.md` | 実装(フローの 4、軽量ルート) | Sonnet | frontmatter に acceptance ガード hook を書く(D17)。コーディング規約スキルに従うと本文に書く(D31)。1 issue の中で使い続け、コンテキストが膨らんだら成果と未完了を報告させて新しいエージェントに引き継ぐ(D29) |
| `kn-doc-reviewer.md` | ドキュメントレビュー(フローの 1・3、impl.md 更新時) | Opus | 書いたのはメインなので、レビューは必ずこちら。毎回新しく起動する |
| `kn-code-reviewer.md` | コードレビュー(フローの 6、軽量ルート、運用ルート) | Opus | 1 体で kn-code-review のチェックリストを全部見る(D23)。毎回新しく起動する。tools は Read / Grep / Glob / Bash / Skill(観点 6 で、リポジトリの外にある規約スキルを Skill ツールで読むため。編集ツールは持たせない) |

- 各エージェント定義の本文に、禁止事項を常設する: 裸の `cd`、dotenv 系ファイルの閲覧、インライン実行、git の書き込み、gh の書き込み(B5)。委譲のたびに手書きしない
- `kn-code-reviewer.md` の本文で、最初に kn-code-review の `references/rules.md` を読むよう指示する。frontmatter での読み込みには頼らない(読まれたかが確かめにくいため)
- メインは acceptance.md と impl.md の author なので、コードレビューも別エージェントに出す(D23。セルフレビューをしない)
- モデルの割り当ては、グローバル CLAUDE.md の「思考・判断は Opus、実装は Sonnet」に合わせた

## 技術的判断

- **acceptance.md の網羅(D12)は、ドキュメントレビューで担保する。** メインが起案した acceptance.md を、別エージェントが design.md の要件と突き合わせる。D12 は手段を決めていないので、既にある reviewer != author の仕組みを使う
- **受け入れテストは実装の前にコミットする。** red の状態をコミットに残し、実装前後の差分で「テストを変えずに通した」ことを確かめられるようにする。そのため acceptance ガードは git の履歴も塞ぐ
- **コードレビューの観点は残し、実行の仕組みを 1 体にまとめる**(D23)。5 レンズの観点(仕様遵守 / impl.md との整合 / バグ・エッジケース / デグレ / 可読性)は有用だったので、コーディング規約(D31)を加えた 6 観点を、チェックリストとして kn-code-reviewer に全部見させる
- **kn-code-reviewer は acceptance.md を読んでよい。** 隔離の対象は実装エージェントだけ(D8・D17)。レビュアーが受け入れ要件を知っていると要件の抜けに気づける。中身が実装エージェントに漏れないよう、指摘はメインが言い換えてから渡す(フローの 6)
- **受け入れテストの置き場所の規約は「パスに `acceptance` を含む」とする。** 具体的な場所は Phase 3 で決める(D14)が、ガードが判定できる条件をここで先に決めておく。場所の選択肢を狭めるのは、ディレクトリ名かファイル名に `acceptance` を入れることだけ
- **レビュー用のエージェントは毎回新しく起動する。** 前回の指摘に引きずられずに見させるため。D29 で使い続けるのは実装エージェントだけ

## 既知の制約

- **Bash を完全には塞げない。** 変数展開・別名・スクリプト経由の読み込みは、コマンド文字列からは判定できない。hook は「普通にやると読めない」水準を目標にし、エージェント定義の本文の禁止事項と二重にする
- **acceptance ガードは Phase 3 まで実地で試せない**(D14)。それまでは、hook 単体に JSON を流して判定を確かめるところまで
- **コミットゲートの修正(A2、D24)が入るまで、`kn-commit-workflow` ではコミットできない。** それまでのコミット(分割案の 1・2 など)はグローバルの `commit-workflow` を起動して行う
- **スキル未配置のままコミットゲートが有効になる問題(B7)は、今回の修正では対処しない。** D24 で判定するスキル名を広げるだけで、「スキルが存在しない」場合の案内は足さない。このリポジトリでは kn- 版がリポジトリ内にあるので起きない
- **「決定を design.md に転記したか」「ドキュメントレビューを走らせたか」を外から確かめる仕組みは作らない(A4、見送り)。** 転記の有無はファイルの中身の判断で、hook では判定できない。代わりに、CLAUDE.md で入口を固定し(B1)、手順を減らして省略の動機を減らす(A6)
- **見送り(D26):** サブエージェントの裸の `cd` を止める hook(B5。エージェント定義の本文に禁止事項を常設して対処)、dotenv テンプレートの表示(B6。閲覧可の判断済みで実害なし)
- **D31 の lint 化は別タスク。** それまでは、規約スキルの遵守を kn-implementer の定義(従うと明記)とコードレビューの 6 つ目の観点だけで担保する
- **差分の外の気づき(このタスクでは直さない):** kn-commit-workflow の push の例外が「PR 作成時の push」だけで、軽量ルート・運用ルートの小さな修正の push に触れていない。kn-dev-workflow の 2 で受け入れテストと文書を 1 コミットにする記述が、kn-commit-workflow の意味単位の分割とぶつかる
- **kn-code-reviewer の tools のうち Grep・Glob が使えない。** 最終レビューで、Skill は使えたが Grep・Glob は無かった(frontmatter には書いてある)。glob メタ文字を含むパスが出てくる Phase 3 で検索に困る可能性がある。原因は未調査
- **見送り:** 最終コードレビュー #7(軽量ルート・運用ルートの小さな修正の周回を、元のタスクから引き継ぐか 0 から数えるか)。D28 の解釈に関わるが、小さな修正で上限に達することは稀なので、実際に起きたときに判断する
