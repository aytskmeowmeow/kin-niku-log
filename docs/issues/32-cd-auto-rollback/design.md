## 目的・背景

- #24 の CD は、デプロイ後の確認(api の `/health` など)が失敗すると、ワークフローを失敗にして通知するだけで、戻すかは人間が判断する(#24 D7)。利用者がいない今は単純さを優先した
- 機能を公開する前に、確認が失敗したら **直前のバージョンへ自動で戻す** 仕組みを CD に入れる
- 完了条件(issue より):
  - デプロイ後の確認が失敗すると、決めた範囲で直前のバージョンに自動で戻り、ワークフローは失敗として通知される
  - ロールバックが実際に行われたことを、ワークフローが確かめている

## #24 から引き継ぐ前提

## 調査結果(2026-11-23 確認)

### `cf` でのロールバックの手段

- `cf`(1.0.0-beta.26)には、Worker 用のロールバックの専用コマンドが無い(`cf cli search` で見つかるのは Pages の `cf pages deployments rollback` だけ。Wrangler の `wrangler rollback` に当たるものは無い)
- 代わりに **`cf workers deployments create`** で、任意のバージョンを 100% にした新しいデプロイを作れる。API は `POST /accounts/{account_id}/workers/scripts/{script_name}/deployments`
  - 必須: `--worker <名前>`、`--strategy percentage`、`--versions '[{"version_id":"<UUID>","percentage":100}]'`(JSON は `@ファイル` でも渡せる)
  - `--bypass-deployment-checks`(API のクエリ `force`): 「古いバージョンへ戻すときに、シークレットが変わっている場合など、通常は止められるデプロイを作る」
  - `--dry-run` あり
- #24 で使っている `cf workers deployments list` の結果は、各デプロイに `versions`(`version_id` と `percentage` の配列)を持つ。**デプロイの前に先頭のデプロイの `versions` を取っておけば、それをそのまま `--versions` に渡して戻せる**
- Cloudflare のダッシュボードのロールバックも、「選んだバージョンを 100% にした新しいデプロイを作る」動き(公式ドキュメント)。上の方法と同じ結果になる
- 非対話の `cf` は、破壊的なコマンドで `--force` が無いと `Aborted.` を出して終了コード 0 で終わることがある(#24 の調査)。`deployments create` がこれに当たるかは未確認。いずれにしても、戻した後に一覧を読み直して確かめる必要がある
- トークンの権限: デプロイの作成は、`cf deploy` が内部で行っていることと同じ種類の操作なので、2 つの Worker の Editor で足りる見込み(未確認)

### Cloudflare のロールバックの制約(公式ドキュメント「Rollbacks」)

- 戻せるのは、直近に公開された 100 バージョンまで。バージョンは 30 日で消える(今デプロイされているものは消えない)
- KV・D1・R2・Queue・Durable Objects などのリソースが、戻し先のバージョンとの間で消えたり変わったりしていると、戻せない(今は 2 つの Worker とも、これらのバインディングを持たない)
- リソース(データ)は戻らない。データの形が変わっていると、古いコードでエラーになりうる
- シークレットは、バージョンの中身(コード・静的ファイル・バインディング・互換性の設定)に含まれず、戻しても値は戻らないと考えられる(ドキュメントに明記は無い)。今は api に本番のシークレットは登録されていない(#20 の申し送りの `DATABASE_URL` は未登録)
- 静的ファイル: 戻した後も、戻す前に読み込まれたページが新しい版のファイルを取りに来ることがある(version skew)。web は Vite のビルドでファイル名にハッシュが付くので、影響は「戻す前に開いていたページが、一部のファイルを取れない」程度
- 反映には時間がかかる(全拠点に届くまでの間、新しい版が応答しうる)

### 今のワークフローでの位置

- `.github/workflows/deploy.yml` の `deploy` ジョブ: 「Deploy api」(前後の ID の比較)→「Smoke test api」→「Deploy web」→「Smoke test web」。どこかで失敗したら後の step は動かない(`if: always()` などは使っていない)
- ロールバックは、失敗したときだけ動く step(`if: failure()`)として足す形になる。`timeout-minutes` は 25(確認の再試行が最悪 13 分ほど)。ロールバックと、その後の確認の分の余裕が要る

## 要件

- デプロイ後の確認が失敗したら、その Worker を **このワークフローがデプロイする前のバージョン** に自動で戻す(範囲ときっかけは D1・D2)
- 戻したことを、ワークフローが Cloudflare の一覧を読み直して確かめ、戻した後にデプロイ後の確認をもう一度流す(D3)
- ロールバックをしても、ワークフローは失敗として終わる(通知は D5)。ログで「戻した」「戻せなかった」が区別できる
- 戻せなかったとき(制約に当たる、`cf` が何もせず終わる、など)と、戻した後の確認が失敗したときは、ワークフローを失敗にし、GitHub の issue を作り(開いていればコメントし)、手でのロールバックの手順に案内する(D4・D5・D7〜D9)
- main からの手動実行で、確認を失敗扱いにしてロールバックの経路を動かせる(D6)
- 運用文書 `docs/operations/deploy.md` を、自動ロールバックが入った状態に合わせる(手でのロールバックの手順は、自動で戻せなかったときのために残す)

### 範囲外

- デプロイの前に新しい版を本番の外で確かめる仕組み(バージョンだけを上げて Preview URL で確かめてから切り替える、段階的な配分など)。Preview URL は無効にしてある(#24 D9)
- データ(DB)のロールバック。DB はまだつながっていない
- シークレットのロールバック
