## 確認方法について

- 本 issue の要件は、GitHub Actions と Cloudflare の本番環境でしか観測できない。そのため ③ ユーザーの手動確認にする(Actions の実行ログ・実行の概要・Cloudflare のダッシュボード・本番 URL へのリクエストで確かめる)。ログやダッシュボードの読み取りは、ユーザーから実行 ID などを受け取ってメインが手伝ってよい
- ① 自動テストは無い。テスト基盤はまだ入っていない。受け入れテストのコミット(フローの 2)は、acceptance.md と design.md のコミットに置き換える(#24 と同じ)
- 例外の区分:
  - AC-6・AC-7 は design.md の D10 により、マージ前に kn-code-reviewer のコードレビューで確かめる(メインも検証で読み合わせる)。本番を壊さないと起きない経路のため
  - AC-8 は文書の確認なので、マージ前に確かめる(メインが検証で読み合わせ、kn-code-reviewer のレビューでも見る)。③ には含めない。D10 の対象ではなく、#24 の acceptance.md(AC-12・AC-13)と同じ扱い
- 進め方は design.md の D14(#24 D17 と同じ)による。③ の確認はマージ後に行い、結果を impl.md に残す。未達は修正の PR で直す。すべての AC を確かめてから issue を閉じる
- 「直前の版」は、その実行がデプロイする前に、その Worker の Deployments の先頭にあったデプロイの版と割合(`versions`)を指す

## 確認を失敗扱いにした実行(D6・D10)

### AC-1. api の確認が失敗したら、api だけが直前の版に戻る

- 種別: 機能
- 出典: design.md D1・D3・D5・D6・D10・D12
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っている。トークンは今のもの(2 つの Worker の Editor だけ)
- And 実行の前に、Cloudflare のダッシュボードで、`kin-niku-log-api` と `kin-niku-log` の Deployments の先頭のデプロイの版(バージョン ID と割合)を控えておく
- When main からの手動実行で、api の確認を失敗扱いにする入力を指定して実行する
- Then ワークフローは失敗で終わる
- And `kin-niku-log-api` に、この実行のデプロイと、その後の直前の版へのデプロイの 2 件が増えていて、最新のデプロイの版と割合が、控えておいたものと同じ
- And `kin-niku-log` の Deployments は増えていない(web はこの実行でデプロイされていない)
- And 実行ログの error の注記(annotation)に、api を戻したことと、戻した版が出ている。ログには、戻したことを一覧で確かめた結果と、戻した後の確認が通ったことも出ている
- And 実行の概要(Job summary)に、api を「戻した」ことと、戻した版が書かれている
- And GitHub の issue `[運用] CD の自動ロールバックに失敗した` は作られておらず、同じタイトルの open な issue があっても、コメントは付いていない
- And 本番の api の `GET /health` が 200 を返す
- And 権限が足りずに戻せなかった場合は、D12 のとおり必要な権限を最小限足して再び実行し、上の Then はその再実行で判定する。1 回目の実行で作られた issue は想定どおりとして扱い、再実行で戻せたことを確かめてから閉じる。足した権限が `docs/operations/cloudflare-api-token.md` と #23 の design.md に書かれている

## 本番を壊さないと起きない経路(D10。コードレビュー)

### AC-6. 戻すきっかけと「戻せなかった」の判定が設計どおり

- 種別: 機能
- 出典: design.md D1〜D4・D6・D10・D11・D15・D16・D18
- 確認方法: コードレビュー(D10)
- Given 本 issue の PR の差分
- When kn-code-reviewer がワークフローを読む
- Then 次のすべてを満たす:
  - (1) デプロイ後の確認が失敗したら、その Worker だけを、その実行がデプロイする前に取っておいた版に戻す。api の確認が失敗したら web はデプロイしない
  - (2) デプロイの step が失敗し、デプロイの前後で一覧の先頭が変わっていた(新しいデプロイが作られていた)ら、その Worker を戻す。先頭が変わっていなければ戻さない。戻した後は、(1) で戻したときと同じく、一覧での確認(AC-5)と、戻した後の確認を行う
  - (3) デプロイの前に戻し先(一覧の先頭のデプロイの `versions`)を取れなかったら、デプロイせずに失敗にする。このときは issue を作らない(D11)
  - (4) デプロイの後に一覧の取得に失敗して、新しいデプロイが作られたか判断できないときは、「戻せた」とは扱わず、「戻せなかった」と同じに扱う
  - (5) 戻すときに、Cloudflare の止める仕組みを強制で外す指定(`--bypass-deployment-checks` など)を使っていない
  - (6) `cf` が何もせず終了コード 0 で終わっても、一覧の読み直し(AC-5 の判定)で「戻せなかった」になる。戻した後に一覧を読み直せなかった(一覧の取得そのものが失敗した)ときも「戻せなかった」として扱う(D18)
  - (7) 戻すコマンドが失敗した(Cloudflare に止められた場合を含む)ときも、そこで処理が止まらず、「戻せなかった」として扱われ、AC-7 の通知まで進む
  - (8) ロールバックをした実行、戻せなかった実行は、どれもワークフローが失敗で終わる。失敗を成功に変える指定(`continue-on-error` など)で、失敗が隠れていない
  - (9) 確認を失敗扱いにする入力は、main からの手動実行のデプロイ直後の 1 回目の確認だけに効き、戻した後の確認には効かない(D6・D15)
  - (10) `deploy` ジョブの `timeout-minutes` が 40 分になっている(D16)

### AC-7. 戻せなかったとき・戻した後の確認が失敗したときに、ログと issue で知らせる

- 種別: 機能
- 出典: design.md D5・D7・D8・D9・D10・D13・D17
- 確認方法: コードレビュー(D10)
- Given 本 issue の PR の差分
- When kn-code-reviewer がワークフローを読む
- Then 次のすべてを満たす:
  - (1) 戻せなかったとき(AC-6 の (4)・(6)・(7) を含む)と、戻した後の確認が失敗したときに、タイトル `[運用] CD の自動ロールバックに失敗した`、ラベル `human`・`ops` の issue を作る
  - (2) 同じタイトルの open な issue があれば、新しい issue を作らず、その issue に今回の実行の URL と状況をコメントする
  - (3) issue の本文・コメントに、対象の Worker、「戻せなかった」か「戻したが、戻した後の確認が通らない」か(戻した場合は戻した版)、実行の URL、手でのロールバックの手順(`docs/operations/deploy.md`)への案内がある(D17)
  - (4) 戻せなかったとき、戻したが確認が通らないときに、ログの error の注記と実行の概要に、そのことと対象の Worker が書かれる。戻したが確認が通らないときは、戻した版も書かれる(D5)
  - (5) 戻せたとき(戻した後の確認も通ったとき)は、issue を作らず、コメントもしない
  - (6) issue を作る権限(`issues: write`)は、issue を作るジョブにだけ付いている(D13)
  - (7) issue の作成と重複の判定(同じタイトルの open な issue を数える)が、`.github/workflows/cf-token-expiry-reminder.yml` と同じ形になっている(D10)
  - (8) issue を作る処理が失敗しても、ワークフローは失敗で終わる(成功にならない)
