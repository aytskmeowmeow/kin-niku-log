## 技術的判断

### 運用文書の置き場所

- `docs/operations/` を運用文書の置き場として新しく作る。#20 の申し送り(本番シークレットの登録、Neon のブランチ構成など)で、運用手順の文書は今後も増える見込みのため
- `docs/<slug>/` は issue にしないタスクの文書置き場(kn-task-docs)なので、`operations` がタスク名と紛れないよう、`docs/project-overview.md` の「タスク管理の運用」に「運用文書の置き場(タスクの文書ではない)」と明記する

### 期限日の書き方と意味

- 運用文書に `- 有効期限: YYYY-MM-DD` の行を 1 つだけ置く(D9)。行頭が `- 有効期限: ` の行を数え、その後ろの値を別に検査する。値は `YYYY-MM-DD` の実在する日付か `未発行` だけを受け付け、それ以外(`2027/02/14`、前後の余計な文字など)は invalid(形式が違う)にする
- 行頭が一致する行が 0 件なら invalid(行が無い)、2 件以上なら invalid(行が複数ある)にする。黙って誤った行を読むのを防ぐため。運用文書の中で書式の例を示すときは、行頭に `- 有効期限: ` が来ない書き方にする(運用文書にも注記する)
- 書く日付は **Cloudflare のトークンに設定した終了日の値そのもの**。調査結果 4 の「日付は UTC 0 時単位」から、**終了日の UTC 0 時(日本時間 9:00)に使えなくなると推定** し、安全側に倒してその解釈で判定する。初回の発行時に、ユーザーがダッシュボードに表示される失効日時を確かめてメインに伝える(実装状況 8)。推定と違っていたら(例: 終了日の終わりまで使える)、メインが共通スクリプトの判定と運用文書を直す。D11 のカレンダーの日付にも及ぶ場合は、仕様の判断としてユーザーに上げる
- 判定は UTC の日付で行う。残り日数 = 終了日 − 今日(UTC)。残り 15 日以上は ok、1〜14 日は due(D9 の「14 日前から」)、0 以下は expired
- トークンの発行前は `- 有効期限: 未発行` と書く。この値のときはどちらの仕組みも何もしない(発行前という一時的な状態のため)

### 共通スクリプト `scripts/cf-token-expiry.sh`

- hook とワークフローで判定を二重に書かないため、判定を 1 本にまとめる
- 運用文書のパスは、スクリプト自身の場所からリポジトリのルートを求めて解決する(hook の実行時のカレントディレクトリにも、ワークフローの作業ディレクトリにも依存しない)。テスト用に、第 1 引数で運用文書のパスを上書きできるようにする
- テスト用に、今日の日付を環境変数 `CF_TOKEN_EXPIRY_TODAY`(`YYYY-MM-DD`)で上書きできるようにする
- 出力: 標準出力に 1 行で状態を返す。`not-issued` / `ok` / `due` / `expired`(期限日と残り日数を添える)/ `invalid`(行が無い・行が複数ある・形式が違う・実在しない日付。理由を添える)。終了コードは常に 0 で、呼び出し側が状態で分岐する
- 日付の計算は macOS(BSD の `date`)と Linux(GNU の `date`)の両方で動くようにする。hook はローカルの macOS と、kn-implementer の VM(Linux。VM の作業場所には `.claude/` も書き出される)の両方で動きうる。ワークフローは Linux で動く
- しきい値の 14 日はスクリプト内の定数にする(D9)

### SessionStart hook

- SessionStart hook の標準出力は Claude の文脈に入る(Claude Code の仕様)。`due` / `expired` / `invalid` のときだけ、Claude に「最初の返答の冒頭でユーザーに伝えること」と運用文書のパスを含む短い文を出す。`ok` / `not-issued` のときは何も出さない
- `invalid` も黙って無視しない。期限日の行が壊れたまま気づかないと、リマインドが止まったことにも気づけないため。同じ理由で、共通スクリプトが見つからない・失敗したときも、短い警告を出す
- どの場合も終了コード 0 で終える(セッションの開始を妨げない)
- プロジェクトのディレクトリは Claude Code が hook に渡す `CLAUDE_PROJECT_DIR` から得る
- matcher は付けない(startup / resume / clear / compact のすべてで動く)。clear・compact の後は前の会話が文脈に残らないので、伝え直してよい。1 つのセッションで何度か伝わることは許容する

### 定期実行ワークフロー

- トリガー: `schedule`(毎日 1 回、UTC 0:17 = JST 9:17。毎時 0 分の混雑を避ける)と `workflow_dispatch`(動作確認用。入力 `today` で今日の日付を上書きできる)
- 権限: `contents: read` と `issues: write` だけ。Cloudflare のシークレットは参照しない(Environment も使わない)
- 外部のアクションは `actions/checkout` だけを使い、タグではなくコミット SHA で固定する(タグの付け替えによる差し替えを防ぐ)。取り出すのは運用文書と共通スクリプトだけ(sparse checkout)
- `due` / `expired` / `invalid` のとき、`gh issue create` で issue を起こす。タイトルは `[運用] Cloudflare API トークンの入れ替え期限`、ラベルは `human` と `ops`(D10)。**同じタイトルの open な issue があれば作らない**(毎日重複して起こさない)。invalid のときも同じタイトルで起こし、本文で状態(期限が近い / 切れた / 期限日が読めない)を分けて書く。開いている issue は常に 1 件。本文は作成時点の状態で、その後に状態が変わっても(due → expired など)更新しない。対応が要ることを知らせるのが目的で、現在の状態は運用文書とセッションのリマインドで分かるため
- issue を閉じるのは人間。入れ替え後の期限日の更新が main にマージされてから閉じる(先に閉じると、翌日のワークフローがまた起こす)

### トークンの入れ替えは新規発行を基本にする(Roll を使わない)

- design.md 調査結果 4 では Roll を「ローテーションに使える」としたが、運用文書の手順は **同じ設定のトークンを新規発行し、切り替えてから古いトークンを削除する** 形にする
- 理由 1: Roll 後の有効期限の扱い(延びるか、元の期限のままか)は公式ドキュメントに記載がなく未確認(調査結果 4)。期限付きトークン(D3)では、Roll で期限が延びないと入れ替えの意味がない
- 理由 2: Roll は古い値を即時失効させるので、GitHub のシークレットを更新するまでの間 CD が失敗する。新規発行なら、シークレットを更新してから古い方を消せる
- Roll 後の期限の扱いを確かめられたら、手順を見直す(運用文書にもその旨を書く)
- 漏洩の疑いがあるときは、新規発行より先に古いトークンを削除する。新しいトークンをシークレットに登録するまで CD は動かないが、漏れたトークンを生かしておくより優先する

### 運用文書の手順の要点

- **初回の発行(人間):** Account API トークン、権限は 2 つの Worker の Editor だけ、有効期限 90 日、IP 制限なし(D1〜D3)→ Environment `production` を作り、Deployment branches を `main` だけにする。Required reviewers は今は付けない(#24 で決める)→ Environment secrets に `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` を登録する。アカウント ID は `cloudflare.config.ts` などリポジトリのファイルに書かない(D7)→ カレンダーに期限の 14 日前と終了日の前日の予定を入れる(D11)→ ダッシュボードに表示される失効日時を確かめる(終了日の UTC 0 時に失効するという推定の確認)→ 終了日を運用文書の期限日の行に反映する
- **期限日の更新の経路:** 運用文書の期限日の行は、ブランチ → PR → マージで main に反映する。hook とワークフローは main(ワークフロー)または作業中のブランチ(hook)の運用文書を読むので、main にマージされるまでワークフローは古い期限日のまま。更新の作業は人間が行うか、Claude に依頼する(日付は人間が伝える)。main の更新より前に切ったブランチ・worktree・kn-implementer の VM では、main を取り込むまで古い期限日で hook のリマインドが続く(許容する)
- **入れ替え(期限前):** 同じ設定で新規発行 → Environment secret を更新 → CD を 1 回動かして確認(#24 以降)→ 古いトークンを削除 → 期限日の行を更新して main にマージ → カレンダーを更新 → リマインドの issue を閉じる → リマインドのワークフローが有効になっているかを確かめ、無効なら有効に戻す
- **開発を再開したとき:** 60 日以上リポジトリに動きが無かった後は、リマインドのワークフローが無効になっていないかを確かめ、無効なら手で有効に戻す(自動では戻らない)
- **漏洩の疑い:** 古いトークンを削除してから、上の入れ替えを行う
- **権限の追加:** 権限は #24 の最初の CD で確定する(Worker の Editor だけで `cf deploy` が通るかは未確認。design.md 調査結果 3・D6)。足したときは、運用文書の権限の記述と #23 の design.md を更新する
- **新しい Worker を足すとき:** 人間がローカルから作成し、トークンの対象に足す。運用文書の権限の記述も更新する(D2)
- **ローカルの認証情報:** #24 の完了まではいまの OAuth ログイン。#24 の完了後はふだんログアウトし、必要なときだけログインする(D4)
- トークンの値・アカウント ID は運用文書に書かない(design.md「範囲外」)

## 検証方法

- **共通スクリプト(メイン、macOS):** 一時ディレクトリに置いたテスト用の運用文書と `CF_TOKEN_EXPIRY_TODAY` で、次の場合の出力を確かめる。未発行(not-issued)/ 残り 15 日(ok)/ 残り 14 日(due)/ 残り 1 日(due)/ 当日 = 残り 0 日(expired)/ 期限後(expired)/ 行が無い・行が複数ある・形式違い・実在しない日付(invalid)。Linux 側の分岐は、ワークフローの手動実行(実装状況 12)で確かめる
  - テスト用の運用文書を読ませるため、スクリプトは運用文書のパスを引数で上書きできるようにする(既定は上の「共通スクリプト」の解決方法)
- **hook(メイン):** 一時ディレクトリに共通スクリプトとテスト用の運用文書を本来と同じ相対パスで置き、`CLAUDE_PROJECT_DIR` をそこに向けて hook を直接実行する(日付は `CF_TOKEN_EXPIRY_TODAY` で変える)。due / expired / invalid で文が出ること、ok / not-issued で何も出ないことを確かめる。スクリプトが無い状態は、`CLAUDE_PROJECT_DIR` を空の一時ディレクトリに向けて作り、警告が出て終了コード 0 であることを確かめる
- **hook の登録(ユーザーに確認を依頼、実装状況 10):** 期限日を記入した後(実装状況 9)、ユーザーが `CF_TOKEN_EXPIRY_TODAY` に期限の 14 日前以降の日付を入れて、このリポジトリで新しいセッションを開き、Claude が最初の返答でリマインドすることを確かめる。ファイルは書き換えないので、元に戻す作業は要らない。続けて、環境変数なしで開いたセッションでは何も出ないことも確かめる
- **ワークフロー(ユーザーに確認を依頼、実装状況 12):** マージ後(期限日は記入済み)、`workflow_dispatch` で (1) 入力なし → ok なので issue はできない (2) `today` に期限の 14 日前以降の日付を入れる → issue が 1 件できる(タイトル・ラベルが D10 のとおり)(3) 同じ入力でもう一度 → 増えない (4) `today` に終了日以降の日付を入れる → 実行ログの判定が expired になる(issue は (2) のものがあるので増えない)、を確かめる。確認用の issue は閉じる。not-issued のときに何もしないことは、共通スクリプトの検証だけで確かめる
- **ワークフローの YAML:** actionlint などの機械的な構文検証はしない(未導入)。レビューと上の手動実行で代える
- `bun run lint` / `bun run check-types` / `bun run build` も実行する(リポジトリのツール設定には触れないが、念のため)
- トークンの発行・登録(実装状況 8)は、ユーザーが運用文書の手順どおりに行い、完了を報告してもらう。デプロイが通るかは #24 で確かめる(D6)

## 既知の制約・未解決の疑問

- 開発を止めている期間は、hook(セッションを開かない)もワークフロー(60 日間動きが無いと自動で無効になる)も働かない。カレンダーが最後の歯止め(D8・D9・D11)。無効になったワークフローは、開発を再開しても手で有効に戻すまで止まったまま(GitHub のドキュメントは再有効化の手順を案内している)。運用文書の手順に確認を入れる
- Linux(GNU の `date`)で確かめられるのは、ワークフローの手動実行で通る ok / due / expired だけ。Linux での invalid(実在しない日付など)の判定と、kn-implementer の VM の中での hook の動作は確かめない
- ワークフローの定期実行は、混雑時に遅延・取りこぼしがありうる。14 日の猶予があるので実害は小さい
- Roll 後の有効期限の扱いは未確認。運用文書では新規発行を基本にする
- hook は kn-implementer の VM の中でも動きうる。VM では kn-implementer が非対話で動き、その標準出力がメインへの報告になるので、期限が近い期間は **kn-implementer の報告の冒頭にリマインドが入りうる**。メインはそれを読み飛ばす
