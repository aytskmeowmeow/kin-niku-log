# #24 GitHub Actions から本番環境へ自動デプロイ(CD) — acceptance.md

- 状態: 承認済み(2026-11-19。ユーザーがチャットで承認)
- 出典: `docs/issues/24-cd/design.md`(D1〜D18、#23 からの申し送り、issue の完了条件)
- **実装エージェントには渡さない**

## 確認方法について

- 本 issue の要件の大半は、GitHub Actions と Cloudflare の本番環境でしか観測できない。そのため ③ ユーザーの手動確認にする(Actions の実行ログ・Cloudflare のダッシュボード・本番 URL へのリクエストで確かめる)。ログやダッシュボードの読み取りは、ユーザーから実行 ID などを受け取ってメインが手伝ってよい
- ① 自動テストは無い。テスト基盤は Phase 3 の最初の issue で入る(kn-dev-workflow の「5. 検証」)。受け入れテストのコミット(フローの 2)は、acceptance.md と design.md のコミットに置き換える
- 例外の区分:
  - AC-8 は design.md の D13 により、マージ前に kn-code-reviewer のコードレビューで確かめる(メインも検証で読み合わせる)
  - AC-12・AC-13 は文書の確認なので、マージ前に確かめる(メインが検証で読み合わせ、kn-code-reviewer のレビューでも見る)。③ には含めない。ただし、AC-13 の権限の記述と AC-5 の文書の確認は、マージ後の最初の CD の実行の結果を受けて後続の PR で直し、そこで確かめる(D16・D17)。マージの時点では「権限はまだ確定していない」が残っていてよい
- 進め方は design.md の D17 による。③ の確認(AC-14 を含む)は PR のマージ後に行う(ワークフローが main に入って初めて動く)。結果を impl.md に残す。マージ後の確認で未達が見つかったら、修正の PR で直す。issue を閉じるのは、権限の記述を直す後続の PR もマージし、すべての AC を確かめた後

## main へのデプロイ

### AC-1. main へのマージで、承認なしに api → web の順でデプロイされる

- 種別: 機能
- 出典: design.md D1・D2・D3・D8、issue の完了条件
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っている
- When `apps/`・`packages/` に触れない PR(ドキュメントやワークフローだけの変更)を main にマージする。本 issue の PR が `apps/`・`packages/` に触れていなければ本 issue の PR で、触れていればドキュメントだけの PR を別にマージして確かめる
- Then 承認の待ちなしに CD のワークフローが起動し、成功で終わる
- And 実行ログで、api のデプロイ(とその直後の確認)が終わってから web のデプロイが始まっている
- And Cloudflare のダッシュボードで、`kin-niku-log-api` と `kin-niku-log` の両方に、この実行の時刻のデプロイが 1 件ずつ増えている
- And 本番の api の `GET /health` が 200 を返す

### AC-2. デプロイ前の確認が、デプロイの前にすべて行われる

- 種別: 機能
- 出典: design.md D4・D5、issue の完了条件
- 確認方法: ③ ユーザーの手動確認
- Given AC-1 の実行
- When 実行ログを見る
- Then どちらの Worker のデプロイよりも前に、次がすべて行われ、通っている: `bun run lint`、`bun run check-types`、web と api それぞれのビルド、web と api それぞれの `cf deploy --prebuilt --mode production --dry-run`、api の本番バンドルに `/doc`・`openapi.yaml` の中身・`localhost:3000` が含まれていないことの確認
- And 各アプリのビルドは実行全体で 1 回だけで、デプロイはその成果物を `cf deploy --prebuilt --mode production` で上げている(デプロイのときにビルドをやり直していない)

### AC-3. デプロイ後の確認が、各デプロイの直後に行われ、通る

- 種別: 機能
- 出典: design.md D6・D14、issue の完了条件
- 確認方法: ③ ユーザーの手動確認
- Given AC-1 の実行
- When 実行ログを見る
- Then 次の順に行われ、すべて通っている: api のデプロイ → api の確認(`GET /health` が 200、`/doc` と `/openapi.yaml` が 404、許可オリジン以外の `Origin` を付けたリクエストに CORS の許可ヘッダー `Access-Control-Allow-Origin` が付かない)→ web のデプロイ → web の確認(`/` が 200)

### AC-4. main からの手動実行でデプロイされる

- 種別: 機能
- 出典: design.md D1
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っている
- When Actions の画面から、ブランチに main を選んでワークフローを手動実行する
- Then AC-1〜AC-3 と同じく、デプロイ前の確認 → api のデプロイと確認 → web のデプロイと確認が行われ、成功で終わる
- And Cloudflare のダッシュボードで、両方の Worker にこの実行の時刻のデプロイが 1 件ずつ増えている

### AC-5. 最小権限のトークンでデプロイが通る

- 種別: 非機能
- 出典: design.md「#23 からの申し送り」(#23 D2・D6)、D16
- 確認方法: ③ ユーザーの手動確認
- Given Environment `production` のトークンは、#23 で発行したもの(2 つの Worker の Editor だけ)
- When 最初の CD の実行(本 issue の PR のマージによる push、AC-1、または AC-4 のうち最初のもの)を行う
- Then 最終的に、Editor だけのトークン、または読み取り系の権限を最小限足したトークンで、AC-1 の Then と同じ判定で通る
- And 権限を足した場合は、足した権限が #23 の design.md と `docs/operations/cloudflare-api-token.md` の「トークンの仕様」に書かれている。足さなかった場合は、`docs/operations/cloudflare-api-token.md` の「権限はまだ確定していない」が「確定した(Editor だけで足りた)」に書き換えられている(AC-13 と合わせて、後続の PR で確かめる)

## main 以外・失敗時の振る舞い

### AC-6. main 以外のブランチからの手動実行は、デプロイ前の確認までで終わる

- 種別: 機能
- 出典: design.md D12、#23 D7
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っており、main 以外のブランチ(main と同じ内容でよい)がある
- When Actions の画面から、そのブランチを選んでワークフローを手動実行する
- Then AC-2 のデプロイ前の確認がすべて行われ、ワークフローは成功で終わる
- And デプロイとデプロイ後の確認は行われていない(実行ログに無い、またはスキップされている)
- And Cloudflare のダッシュボードで、どちらの Worker にもこの実行の時刻のデプロイが増えていない

### AC-7. デプロイ前の確認が、壊れたものを検出してワークフローを失敗にする

- 種別: 機能
- 出典: design.md D5・D12・D13
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っている。main から、次のどれか 1 つだけをわざと壊した検証用のブランチを切る(壊し方ごとに 1 本): (a) lint のエラー (b) 型のエラー (c) api の本番バンドルに `localhost:3000` が含まれる変更
- When それぞれのブランチを選んでワークフローを手動実行する
- Then どの実行も失敗で終わり、実行ログで、壊した内容に対応する確認の step が失敗している
- 補足: ほかの確認で先に止まり、対応する確認の step が動かなかった場合は、壊し方を変えてやり直す(例: 型のエラーを lint に引っかからない書き方にする)。壊し方は D5 の確認の抜き取り(D13)。dry-run の失敗と `/doc`・`openapi.yaml` の混入の検出は AC-8 のコードレビューで確かめる。main 以外の実行は D12 によりもともとデプロイしないので、この AC は「確認が失敗を検出すること」だけを確かめる。main で確認がデプロイを止めることは AC-8。検証用のブランチは確認後に消し、main にはマージしない

### AC-8. main で、失敗がそれ以降のデプロイを止め、ワークフローを失敗にする

- 種別: 機能
- 出典: design.md D3・D5・D6・D7・D13・D14・D18
- 確認方法: コードレビュー(D13。本番を壊さないため、①〜③ では確かめない。冒頭の「例外の区分」)
- Given main からの実行(push・手動実行)
- When デプロイ前の確認のどれかが通らない / api のデプロイが失敗する(何も上げずに終わった場合を含む)/ api の確認が通らない / web のデプロイが失敗する(同上)/ web の確認が通らない
- Then デプロイ前の確認が通らなければ、どちらの Worker もデプロイしない
- And デプロイ前の確認は、dry-run の失敗と、api の本番バンドルへの `/doc`・`openapi.yaml` の中身の混入も検出する
- And `cf deploy` が何も上げずに終わった場合(終了コード 0 の場合を含む)も、デプロイの失敗として扱われる
- And api のデプロイが失敗するか、api の確認が通らなければ、web はデプロイしない
- And デプロイ後の各確認は、期待と違う応答(`/health`・web の `/` が 200 以外、`/doc`・`/openapi.yaml` が 404 以外、許可オリジン以外に CORS の許可ヘッダーが付く)で失敗と判定する
- And デプロイ後の確認(api・web とも)は、決めた回数・間隔で再試行してから失敗とする
- And どの失敗でも、ワークフローの結果は失敗(failure)になる。失敗を成功扱いにする設定(`continue-on-error` など)をしていない。通知は GitHub の既定(失敗時のメール)によるため、結果が failure になることで判定する
- And 自動のロールバックはしない

### AC-9. main のデプロイは 1 本ずつ動き、待ちは最新の 1 本だけ残る

- 種別: 機能
- 出典: design.md D10
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っている
- When main からの手動実行を起動し(1 本目)、1 本目が終わる前に、ドキュメントだけの PR を main にマージし(2 本目、push)、続けて main からの手動実行を起動する(3 本目)。全部で 3 本
- Then 1 本目は取り消されずに最後まで走って成功する
- And 2 本目(push)は実行されずに取り消される(push と手動実行が同じ順番待ちに入っている)
- And 3 本目は 1 本目が終わるまで待ち、その後に走って成功する

### AC-10. main 以外からの実行は、main のデプロイの順番待ちに入らない

- 種別: 機能
- 出典: design.md D15
- 確認方法: ③ ユーザーの手動確認
- Given ワークフローが main に入っており、main 以外のブランチ(main と同じ内容でよい)がある
- When main からの手動実行を 2 本続けて起動し(2 本目は待ちになる)、1 本目が終わる前に main 以外のブランチからの手動実行を起動する
- Then main 以外からの実行は、1 本目を待たずに走り始める
- And main の 2 本目は取り消されず、1 本目の後に走って成功する

### AC-11. PR ではデプロイせず、プレビュー URL も無効のまま

- 種別: 機能
- 出典: design.md D1・D9
- 確認方法: ③ ユーザーの手動確認
- Given 本 issue の PR と、AC-1 のデプロイ
- When PR を作る・更新する。AC-1 のデプロイの後に、Cloudflare のダッシュボードで両方の Worker の最新のバージョン ID を見る
- Then CD のワークフローは PR をきっかけに起動しない(PR のチェックの一覧に出ない)
- And 両方の Worker の最新のバージョンの Preview URL(`<バージョン ID の先頭 8 桁>-<Worker 名>.aya-ayatsuki.workers.dev`)が 404(error code 1042)を返す(#20 の確認と同じ方法)
