## 調査結果(2026-11-17 確認)

確認できなかったことは「未確認」、推測で補ったことは「推定」と書いている。

### 1. `cf` の CI 向けの使い方(公式ドキュメント)

公式の GitHub Actions の例は次の形(要約):

- `on: pull_request` と `push: branches: [main]`
- `cf build` で 1 回だけビルド → `cf deploy --prebuilt --mode production --dry-run` で検証 → push のときだけ `cf deploy --prebuilt --mode production`
- シークレット(`CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`)は最後のデプロイの step だけに渡す
- `CF_SEND_TELEMETRY: "false"` でテレメトリを切る

要点:

- `--prebuilt` はビルドを飛ばし、`.cloudflare/output` の Build Output をそのまま上げる。**ビルド時に記録された mode と `--mode` が一致しないと、何も上げずに止まる**(Vite のビルドは指定が無ければ `production` を記録)
- `cf deploy --dry-run` は認証不要で、API を呼ばずに検証する
- CI では非対話で動く。プロンプトは既定値を使い、既定値の無いプロンプトは失敗する。破壊的なコマンドは `--force` が無いと何もせず**終了コード 0** で終わる(ロールバックなどを自動化するときに注意)
- `cloudflare.config.ts` が無いと自動設定がファイルを書き換える。本リポジトリは両アプリとも commit 済みなので該当しない
- Node.js 22.18 以上が必要(本リポジトリは 22.23.5)
- `cf` は devDependency に固定する(本リポジトリは両アプリに `^1.0.0-beta.26`。`bun.lock` で版が固定される)

出典: https://developers.cloudflare.com/cf/ci/

### 2. ロールバックの手段

- `cf` の `deploy` 自体にロールバックのオプションは無い(`cf deploy --help`、1.0.0-beta.26)
- Cloudflare API を直接叩くコマンドとして `cf workers versions list`(バージョン一覧)と `cf workers deployments create`(指定したバージョンでデプロイを作る)がある。これで「直前のバージョンに戻す」はできる見込み(**未確認**: 実際に試していない)
- トークンの Editor ロールでロールバックはできる(#23 調査結果 3)
- ダッシュボードの Worker の「Deployments」からも、人間が手でロールバックできる
- #23 D4 により、CD が動いた後はローカルの `cf` はふだんログアウトしている。人間が手でロールバックするときは、ダッシュボードを使うか、その時だけログインする

出典: `cf cli search` の結果(ローカル、`cf` 1.0.0-beta.26)、#23 design.md

### 3. GitHub Actions の関係する仕組み

- `workflow_dispatch`: Actions の画面から手動で実行できる。Environment `production` は Deployment branches が `main` だけなので、**main 以外のブランチから手動実行しても、シークレットが渡らずデプロイは失敗する**(安全側)
- `concurrency`: 同じグループのワークフローを 1 本ずつ動かす。`cancel-in-progress: false` なら、実行中のものは最後まで走り、待っているものは最新の 1 本だけ残る(古い待ちは取り消される)
- ワークフローが失敗すると、既定では実行した人(main への push ならマージした人)に GitHub からメールで通知が届く(通知設定による)
- public リポジトリでは標準ランナーが無料

### 4. 現状のリポジトリ

- `.github/workflows/` には #23 のトークン期限のリマインドだけがある。**PR 時の CI はまだ無い**
- ビルドは `bun run build`(turbo 経由で各アプリの `vite build`)。#20 の手動デプロイ手順は各アプリで `cf build` → `cf deploy --dry-run` → `cf deploy`
- #20 の手動デプロイ手順(`docs/issues/20-initial-deploy/impl.md` の「デプロイ手順」)の確認項目: web の `/` がプレースホルダー / api の `GET /health` が 200 / api の `/users`・`/doc`・`/openapi.yaml` が 404 / 許可オリジン以外の `Origin` に CORS ヘッダーが付かない / プレビュー URL が発行されていない
- #20 で web → api の順にデプロイしたのは、web をデプロイして初めて web のオリジン(api の許可オリジン)が確定したため。今はオリジンが確定しており、この理由は無くなっている

- 残っている指摘(コードレビュー第 4 回、2 件):
  1. 手順 2 で、戻す対象に含めるかを「Cancel した run がデプロイの step を終えていたか」で決めている。Cancel がデプロイの step の途中で効くと、step は完了と表示されないのに、Cloudflare 側ではアップロードが済んで新しい版が出ていることがある。step の状態ではなく、Cancel の後に両 Worker の Deployments の先頭を見て判断するべき
  2. 「Cancel した run が Cancelled になったことを確かめる」とあるが、Cancel の前に終わった run は Success / Failure になる。手順どおりに読むと先へ進めない
- 原因の見立て: 実装の不備というより、人が手で行う障害時の手順に、GitHub Actions の順番待ち・Cancel の細かい挙動がからむため、レビューのたびに新しいエッジケースが見つかっている。手順を細かく書くほど、次の穴が見つかる形になっている
- 選択肢:
  - ① さらに続ける: 上の 2 件を、レビュアーの案どおり「Cancel の後に、両 Worker の Deployments の先頭を見て、Cancel した(または Cancel の前に終わった)run が出したデプロイがあれば戻す対象に含める」に書き換える(実装第 5 回)。この節への以後の指摘は、戻さずに既知の制約として記録する
  - ② スコープを縮めて受け入れる: 今の手順のまま受け入れ、残る 2 件は deploy.md の手順の下に注意として 1〜2 行で書く(実装には戻さず、メインが文書の注記として足す)
  - ③ 設計を見直す: Cancel をやめ、「Disable の後、実行中・待ちの Deploy がすべて終わるのを待ってから、Deployments の先頭を見て戻す」に単純化する。Cancel の挙動に依存しなくなるが、障害時に最大 50 分前後(25 分 × 2 本)待つことがある
  - ④ 別タスクに切り出す: 手でのロールバックの手順の詰めは #32(自動ロールバック)に回す。#24 では今の手順のまま残し、#32 で自動化と合わせて決める
- トレードオフ:
  - ①: 指摘はほぼ解消する見込み。もう 1 周分の実装とレビューがかかる
  - ②: いちばん早い。手順には穴が残るが、注記で読み手に知らせる。今は利用者がおらず、手でのロールバックを使う場面は少ない
  - ③: 手順が単純になり、穴の元(Cancel)が無くなる。障害時の待ち時間が長い
  - ④: #24 を早く閉じられる。#32 で自動ロールバックを入れると、手でのロールバックの手順も見直すことになるので、まとめて決めるのは自然。それまでの間、今の手順の穴は残る
- 推奨: **①**。2 件ともレビュアーの案(Deployments の先頭を見て判断する)で同時に解消でき、変更は手順 2 の数行で済む。以後この節への指摘は、戻さずに既知の制約として記録する
